# 와이어프레임의 구성·조작 방식 탐색

## 적용 시점과 고정 조건

A3에서 화면 책임과 상태를 확인받은 뒤, B의 세 구조안을 그리기 **전에** 적용한다. 같은 사용자 과업, 확정된 기능·정보 ID, 실제 콘텐츠, 기기 폭, 초기·포화 상태를 고정한다. 색·폰트·그림자·재질은 비교 변수가 아니다. 기존 제품의 승인된 플랫폼·접근성·브랜드 제약을 지킨다.

작업할 때 접근 가능한 **현존 앱의 실제 화면**을 구조 참고 자료로 찾는다. 먼저 [iOS·One UI 기본 앱 21개 화면 관찰](mobile-app-study.md)과 그 출처를 목적·상태별로 확인하고, 같은 역할의 다른 앱 화면도 찾아 구조 편향을 줄인다. 앱 이름·플랫폼·버전/확인일·화면·상태·사용자가 한 조작·보이는 결과를 기록한다. 공식 화면, 실제 실행 화면, 제공된 스크린샷의 증거 수준을 구분한다. 정적 사진만 봤다면 열림·닫힘·뒤로가기 동작을 관찰했다고 쓰지 않는다. 원본 이미지는 배포 스킬에 저장하지 않고 출처와 관찰 결과만 남긴다. 레퍼런스의 색을 B 구조안으로 복사하지 않는다.

## 의미가 같은 대안끼리 비교

먼저 A1 기능·정보와 A2 흐름을 `역할 → 트리거 → 결과 → 복귀`로 정리한다. 역할이 같아도 공개 위치와 사용 순서는 다를 수 있다. 각 주요 역할에서 두 가지 이상의 적합한 **구성 후보**를 찾고, 아래 축 중 실제 과업 차이가 큰 것을 B의 구조안에 적용한다. 모든 축을 억지로 바꾸지 않는다.

| 비교 축 | 구조 후보와 판단 근거 |
| --- | --- |
| 선택 위치 | 짧은 즉시 선택은 화면 안의 선택 목록·세그먼트, 많은 선택지는 별도 화면·검색, 현재 맥락을 보며 잠깐 고르는 일은 시트나 메뉴를 비교한다. `select`/드롭다운을 기본값으로 두지 않는다. |
| 상세 공개 | 같은 맥락에서 한두 항목만 펼치는 disclosure/expand, 긴 상세·독립 과업은 상세 화면, 잠깐 확인하고 돌아오는 것은 팝오버·시트를 비교한다. 팝업을 기본값으로 두지 않는다. |
| 주 행동 | 본문에 붙은 행동, 하단 고정 행동, 행별 행동, 선택 후 나타나는 행동을 과업의 도달 시점과 화면 공간으로 비교한다. |
| 탐색·정보 묶음 | 목록→상세, 한 화면의 구역·목차, 단계형 흐름, 마스터·디테일, 질문에 따라 드러나는 정보 묶음을 비교한다. |
| 보조 행동 | 화면에 직접 노출, 메뉴/더보기, 문맥 메뉴, 별도 관리 화면을 빈도·위험·발견성으로 비교한다. 숨겨도 되는 행동인지 확인한다. |

같은 의미라도 대안 사이에 **진입·보이는 정보·조작 수·뒤로/닫기·포커스·스크롤 보존**이 어떻게 달라지는지 적는다. 선택 시트는 짧은 문맥 과업, 확장은 주변 내용을 함께 읽는 일, 별도 화면은 복잡하거나 긴 작업에 맞는지를 실제 자료로 시험한다. 플랫폼 관례가 우선이며, 탭·스위치처럼 의미가 다른 요소를 외형만으로 바꿔 넣지 않는다. 파괴적 행동이나 필수 정보는 숨겨진 제스처·더보기만으로 접근하게 만들지 않는다.

## B의 세 안을 만드는 계약

세 안 모두 확정 기능·필수 정보·핵심 흐름을 포함한다. 각각의 **주된 구조 원리**와 적어도 하나의 역할에서 쓰는 공개·선택·이동 방식이 실제로 달라야 한다. 예를 들어 같은 필터 행을 세 가지 위치에 옮기거나, 같은 화면의 색·R·카드 수만 바꾼 것은 세 안으로 세지 않는다. 반드시 버텀시트·확장·별도 화면을 각각 하나씩 넣으라는 뜻도 아니다. 과업에 맞는 후보를 고른다.

| 대안 ID | 참고한 앱·화면·관찰 근거 | 주된 구조 원리 | 역할별 컴포넌트/공개 방식 | 같은 과업의 진입→결과 | 초기·포화·좁은 폭 렌더 | 얻는 것·잃는 것 |
| --- | --- | --- | --- | --- | --- | --- |

후보별로 화면 수, 첫 화면의 정보 발견성, 주 행동 도달, 추가 조작, 닫기·뒤로 결과, 키보드/스크린리더 경로, 긴 내용과 큰 글자에서의 변화를 비교한다. 세 안을 실제 저충실도 화면과 주요 열림 상태까지 렌더해 나란히 보여 준다. 참고 앱이 서로 달라도 사용자의 과업에 맞지 않으면 채택하지 않는다. 왜 해당 앱의 구조가 이 과업에 맞는지와 어디서는 다르게 설계했는지를 기록한다.

## 증거와 실패 판정

각 안의 레퍼런스는 앱·화면·상태와 관찰한 구성 원칙까지 추적한다. 출처가 없는 구조안은 제안으로 표시하고, 실제 앱에서 관찰했다고 쓰지 않는다. 선택 컴포넌트의 의미·동작을 정적 화면에서 추측한 경우에는 확인 전까지 미검증이다. 세 안이 색·모서리·크기만 다르거나, 실제 기능·정보가 서로 달라 공정하게 비교할 수 없거나, 대안의 열림 상태가 없으면 B 제시 전 수정한다. [구성안 기록 검사기](../scripts/check_wireframe_variants.py)는 이 기록의 공백만 찾는다. PASS가 구조의 적합성·고유성을 자동 증명하지 않는다.
