# 넓은 모션 어휘를 앱·웹·문서 설계에 적용하기

이 지식은 [14개 상위 그룹의 온톨로지](../knowledge/motion-ontology.json), [별칭·변형·비동일 판정](../knowledge/motion-equivalence.json), [19개 원본 세부 유형의 사용 정책](../knowledge/motion-family-policy.json), [414개 용어별 기록](../knowledge/motion-taxonomy.json), [414개 원본 동작 설명과 제작 문장](../knowledge/motion-source-behavior.json), [항목별 방향·시간·수치 제작 단서](../knowledge/motion-construction-cues.json), [확정 공통 모션 전용 시연](../samples/motion-verified-lab.html), [원본 용어 임시 시연 보관함](../samples/motion-414-lab.html), [43개 앱용 제작 레시피](../assets/layout/oneui9-motion-recipes.mjs), [One UI 스타일 앱 시연](../samples/oneui9-motion-lab.html)으로 나뉜다. **414개는 고유 동작 수가 아니라 수집된 용어 수**다. 각 용어에 웹 맥락·변화 축·구현 경로 후보·시작 사건·정적 및 움직임 감소 대안·유사 용어 후보를 보관한다. 원본 문장 수집은 원본 시연과 내부 결과의 일치를 증명하지 않는다. 원본 용어 보관함의 414개 장면은 실행 가능한 검토용 스케치이며, 기본 시연 목록은 확정 공통 동작군의 통일 이름만 보여준다. 현재 414개 전체의 원본 동작 재현은 검증되지 않았다. 2026-10-28 검사에서는 키프레임 구성이 169개이고 중복 그룹이 69개다. 43개 앱 레시피는 별도 맥락·계기·목적을 가진다. 항목의 WebGL·영상 합성 경로는 제작 선택지이며 브라우저 스케치만으로 원래 매체 수준의 구현을 증명하지 않는다. 시간과 시연 배율은 [모션 시간과 검토 속도](motion-timing.md)에 따라 결정한다. 외부 스킬·사이트·런타임을 호출하지 않는다.

## 제작 지시를 시연·구현에 연결

[모션 예시와 중복 판정 계약](motion-sample-selection.md)을 적용한다. 상위 그룹은 탐색용이며 샘플 컴포넌트의 종류를 결정하지 않는다. 모션마다 핵심 변화를 가장 명확히 보일 수 있는 객체·상태를 고르고, 시작·중간·끝을 직접 비교한다. 같은 모션의 별칭과 서로 다른 뜻인데 구현만 중복된 오류를 구분한다.

대표 명칭과 변형의 원본 관계가 확정된 항목부터 [원본 근거 모션 제작 모듈](motion-production.md)을 적용한다. 소스 용어 수, 대표 동작 수, 별칭·변형·조합 수, 내부 구현 PASS 수를 분리해 보고한다.

모션 이름만으로 코드를 고르지 않는다. 항목마다 **적용 대상 → 실행 계기 → 시각 객체의 변화 순서 → 방향·수치·시간 → 종료 상태 → 움직임 감소 → 시작·중간·끝 프레임 검증**을 한 계약으로 적는다. 내부 제작 단서는 요청 예문에서 방향·수치·시각 객체를 구조화한 것이다. 외부 문구를 그대로 실행하거나 복사한 템플릿이 아니다. 414개 시연 페이지의 접힌 제작 지시에서 각 계약의 단서를 보고, 실제 결과가 동작 이름과 다른 경우 엔진을 고친다. 실제 제품에서는 해당 화면의 역할과 GT가 제작 단서보다 우선한다.

**시연 검증 게이트:** 원본 페이지의 실제 시연을 시작·중간·끝 시점에서 관찰하고, 해당 효과의 대상·형태·방향·시간·종료 상태를 적는다. 내부 시연과 같은 시점의 프레임을 비교한다. 414개 전체의 애니메이션 키프레임 구성을 수집해 중복 그룹을 검출하고, 같은 계열 안의 서로 다른 이름이 같은 움직임으로 떨어지면 FAIL로 기록한다. 이름이나 수치만 바꿔 중복 검사를 통과시키지 않는다. 재생 픽셀 변화와 DOM 애니메이션 존재는 동작 일치의 증거가 아니다. 브라우저에서 표현할 수 없는 영상 합성 효과는 대체 스케치로 명시하고, 원본 재현으로 표시하지 않는다.

예: 스퀴즈 라인은 앞 화면이 **좌우로 모여 세로 선**이 되고 새 화면이 그 선에서 펼쳐져야 한다. TV 오프는 **위아래로 모여 가로선·점**이 된 뒤 새 화면이 반대로 켜지거나 종료 상태를 유지해야 한다. 두 동작을 같은 축의 축소 효과로 합치면 실패다. 화면 전환과 종료는 별도 상태로 검토한다.

## 1. 선택 순서

1. 화면의 **사건**을 적는다: 누름, 선택, 열림, 삭제, 재정렬, 진행, 데이터 갱신, 설명 단계 공개 등.
2. 사용자가 알아야 할 **변화**를 정의한다: 상태, 위치, 계층, 크기, 순서, 초점, 시간, 값 중 무엇인가.
3. 정지 화면의 의미 전달을 먼저 확보한다. 모션을 끄면 사라지는 정보는 설계 실패다.
4. 아래 어휘에서 성격이 다른 후보를 좁힌다. `효과 이름 + 방향/대상 + 시간 + 강도 + 종료 상태 + 취소/역전`으로 시안을 만든다. 강도와 속도는 별개 축이다.
5. 같은 실제 콘텐츠로 재생·중단·빠른 재입력·모션 감소를 비교하고 확인 D에서 대상과 느낌을 사용자와 정한다. 선택한 모션의 실제 화면 구현을 다시 검수한다.

## 2a. 웹 작업에서 조회하는 방법

웹에서는 사용 위치를 **제품 조작 / 데이터 설명 / 읽기·스크롤 서사 / 캠페인·전시 장면**으로 먼저 나눈다. 같은 `줌`이라도 이미지 확대 조작, 제품 공간 카메라, 랜딩 타이틀 강조는 입력·종료·중단 방식이 다르다. 카탈로그의 `webContexts`는 후보 맥락이고 `webFit`은 기본 판정이다. 실제 화면의 역할과 콘텐츠를 확인한 뒤 선택한다.

| 경로 후보 | 알맞은 변화 | 제작 시 확인 |
| --- | --- | --- |
| CSS transition/keyframes | 단순 상태색·이동·크기·투명도 | `transition: all` 대신 속성 지정, 숨긴 요소의 포커스 차단 |
| Web Animations API | 재입력·역전·중단이 있는 화면 전환과 목록 이동 | 취소 시 최종 상태와 ARIA를 동기화 |
| SVG 경로·마스크 | 아이콘 선 그리기, 차트, 흐름도, 공개 영역 | 라벨·화살촉·값을 최종 정적 도식에도 유지 |
| Canvas/WebGL | 입자·절차적 배경·3D 카메라·공간 분해 | 저사양·축소 모션·정지 프레임 대안, 전경 텍스트 대비 |
| 영상 합성 | 실제 영상의 시간 압축·광학 효과 | 영상 없는 UI를 효과 이름만으로 흉내 내지 않음 |

스크롤은 제품의 기본 이동이다. 스크롤 위치에 붙인 연출은 내용의 읽기·조작을 방해하지 않을 때만 쓰고, 키보드 이동·뒤로가기·모션 감소에서도 의미가 유지되어야 한다. 점멸·스트로브 등 감각적 효과는 반복 사용자 과업에 붙이지 않는다. 데이터 모션은 실제 값·단위·분모를 보존한다. 웹용 레시피를 만들 때는 `trigger, target, from/to, duration/easing, interrupt/reverse, staticFallback, reducedMotion, browser route, rendered evidence`를 같은 기록에 둔다.

## 3. 자주 혼동되는 움직임

| 비교 | 결정 기준 | UI 적용 예 |
| --- | --- | --- |
| 팬 ↔ 트랙 | 제자리서 시야가 도는가, 관찰 위치가 옆으로 이동해 전·후경 차이가 생기는가 | 지도/공간 프리뷰에서만 구별. 목록 스크롤을 팬으로 부르지 않음 |
| 줌 ↔ 달리 | 화면 전체가 비례 확대되는가, 카메라 위치 변화로 원근이 달라지는가 | 사진 확대는 줌, 3D 공간 진입은 달리 |
| 스냅 줌 ↔ 펀치 인 | 몇 프레임의 확대 과정이 있는가, 중간 없이 컷으로 바뀌는가 | 중요한 그래프 지점 강조 시 목적에 맞게 선택 |
| 마스크 리빌 ↔ 라인 드로 | 면 안의 내용이 드러나는가, 선 자체가 그려지는가 | 제목 공개와 흐름 화살표에 각각 대응 |
| 오버슈트 ↔ 안티시페이션 | 목표점을 지나 되돌아오는가, 움직이기 전에 반대 방향으로 준비하는가 | 버튼 완료 반응과 드래그 출발에 각각 조건부 |
| 스태거 ↔ 팔로 스루 ↔ 오버래핑 | 별도 요소들의 시작 시차인가, 본체 정지 뒤 딸린 끝부분의 관성인가, 한 몸의 부위 시차인가 | 목록 순차 등장과 물성 시연을 혼동하지 않음 |
| 카운트업 ↔ 오도미터 | 숫자 값만 변하는가, 자릿수 바퀴가 굴러가는가 | 실적/포인트 갱신 시 판독 가능한 최종값 유지 |
| 블러 ↔ 트레일 ↔ 스미어 | 흐린 번짐인가, 또렷한 잔상인가, 프레임 형태 자체의 늘어짐인가 | 빠른 장면 표현에서만. 일반 버튼 피드백에는 거의 불필요 |
| 화면 분할 ↔ 화면 속 화면 | 동등한 장면을 나란히 보는가, 큰 장면 위에 작은 보조창을 겹치는가 | 비교 페이지와 영상 통화 미리보기에 각각 대응 |

## 4. One UI 스타일 실험의 한계와 연결

[One UI 9 화면 관찰](mobile-app-study.md)의 따뜻한 전체 바탕, 큰 제목과 한 손 조작을 위한 상단 여백, 둥근 흰 그룹 표면, 선명한 보라 강조를 실험 페이지에 적용했다. 이는 저장된 화면 표본의 **관찰 기반 재구성**이며 공식 One UI 9 모션 토큰이나 삼성 승인 디자인이 아니다. 각 레시피의 색·시간·곡선은 이 실험을 위해 정한 값이다. 실제 앱에서는 해당 기기·플랫폼의 상태, 뒤로가기 제스처, 모션 감소 설정을 확인하고 다시 결정한다.

실험 페이지에는 43개 동작이 재생되며 전체 414개는 계열별 이름으로 펼쳐 볼 수 있다. 해당 페이지는 **시연을 위해 자동 반복을 기본 활성화**한다. 기기에서 움직임 감소를 요청해도 먼저 재생 상태를 명시하고, 페이지의 `움직임 줄이기` 버튼으로 정적 결과를 비교한다. 실제 제품에는 이 시연 기본값을 복사하지 않고 기기 설정을 따른다. 앱에 맞지 않는 영상 전용 효과를 One UI의 정상 상호작용인 것처럼 보이게 만들지 않는다. 새 레시피를 추가할 때 `역할/사건 → 실제 데이터와 상태 → 대상·시간·곡선 → 정적/감소 대안 → 작동하는 시연 → 경계 시험`을 함께 기록한다.
