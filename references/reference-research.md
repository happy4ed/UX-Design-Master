# 레퍼런스 조사

## 사용자가 특정 레퍼런스를 말한 경우: 조사부터 시작

사용자가 URL·앱 이름·화면·스크린샷·이미지를 지정하면 **시각 작업 전에 그 원본을 먼저 찾고 실제 비주얼을 확인한다.** URL은 해당 페이지와 같은 제품의 관련 화면을 열고, 앱은 공식 화면·스토어 화면·접근 가능한 실제 캡처에서 이름·버전·상태를 확인한다. 제공된 스크린샷은 직접 읽고 출처가 언급되면 해당 원본도 찾는다. 원본에 접근할 수 없으면 검색 결과의 썸네일 수준을 명시하고, 보지 못한 동작·간격·색을 사실로 쓰지 않는다. 이 조사와 구조 A1~A3는 병행할 수 있지만, 시각 가안은 확인 B의 와이어프레임을 바꾸거나 앞당기지 않는다.

확인한 원본마다 **레퍼런스 스타일 명세**를 만든다. 화면/상태·뷰포트·캡처 시점과 근거를 붙여 화면 전체 바탕→Z 층별 표면·경계·그림자·블러→그리드·정렬선·여백→타입 계층→색 역할→아이콘·이미지→선택·호버·전환 상태 순으로 기록한다. 관찰값(px·색 표본), 추정값, 새 제품에 채택할 규칙을 구분한다. 스크린샷만으로 확인할 수 없는 터치 영역·모션·반응형 규칙은 미확인으로 남긴다. 복수 화면에서 반복된 값과 한 화면의 우연한 값도 구분한다.

확인 B 뒤에는 **승인된 같은 구조와 실제 콘텐츠**로 작은 시각 가안을 렌더한다. 원본과 가안을 같은 화면 크기·상태에서 나란히 놓고, 그리드/정렬·타입 크기와 무게·간격·표면/Z 깊이·색 역할·이미지 비율·상태 표현별로 `원본 관찰 → 가안 측정 → 차이 → 채택/수정/의도적 변경` 표를 채운다. 단순 픽셀 점수나 분위기 평가로 유사도를 대신하지 않는다. 차이가 반복되면 스타일 명세를 수정하고 다시 렌더한 뒤 확인 C의 시각 방향 후보로 제시한다. 플랫폼 관례, 접근성, 우리 콘텐츠 길이 때문에 달라진 부분은 의도와 값을 기록한다.

웹 원본에 실제 접근할 수 있으면 [실측 디자인 계약](design-brief.md)의 계산 스타일 수집기를 같은 뷰포트·상태의 캡처와 함께 실행한다. 기록의 `reference.sourceType`을 `live-web`으로 두고 `measuredStates[]`에 `stateId`, `viewport`, `capture`, `measurement`, `truncatedNodes`를 연결한다. 표본이 잘렸다면 `limitNote`로 누락 범위를 밝힌다. 색 역할과 Z 층은 자동 수집값에서 바로 확정하지 않고 원본 화면에서 판정한다. 스크린샷만 있는 원본에 DOM 실측을 꾸며 넣지 않는다.

[레퍼런스 비교 기록 검사기](../scripts/check_reference_comparison.py)는 `reference`의 출처·확인일·화면 상태·뷰포트·시각 근거, 웹 원본이면 상태별 실측 근거, `draft`의 승인 와이어프레임·같은 상태·콘텐츠·렌더 근거, `comparisons`의 일곱 축별 관찰·실측·차이·결정을 확인한다. 검사기 PASS는 기록 완전성일 뿐 유사도·사용성·시각 품질의 PASS가 아니다.

**실패 조건:** 원본을 보지 않고 이름의 인상으로 스타일을 만드는 것, 일부 크롭만 보고 전체 화면 규칙을 확정하는 것, 원본의 측정값과 우리 채택값을 섞는 것, 서로 다른 뷰포트·상태를 비교하는 것, 한 가안의 픽셀 유사도만으로 품질을 PASS로 표시하는 것.

## 출처 선택

제품 유형·핵심 과업·정보 밀도·플랫폼·브랜드 성격을 검색 기준으로 삼는다. 직접 경쟁 제품뿐 아니라 같은 문제를 잘 푸는 다른 분야도 살핀다.

후보 소스는 실제 서비스와 공식 앱 화면, 공식 디자인 시스템(예: Apple HIG, Material, GOV.UK), 제품 패턴 자료(예: Mobbin, Page Flows), 웹 큐레이션(예: Awwwards, Land-book, Lapa Ninja), 제작자 사례(예: Behance, Dribbble)다. 이는 고정 추천 목록이 아니다. 해당 시점에 접근 가능한 소스를 확인하고, 과업에 맞게 선택한다. 탐색 인터페이스와 마케팅 랜딩 페이지의 평가 기준을 섞지 않는다.

서로 독립적인 복수 소스를 비교한다. 핵심 후보는 가능하면 원본 화면과 동작을 직접 확인한다. 접근 제한으로 원본을 볼 수 없다면 검색 썸네일만 보고 세부 동작을 추측하지 말고 관찰 범위를 명시한다. 우회 접근을 시도하지 않는다. 브라우징이 불가능하면 제공된 자료로 작업하고 미검증 출처를 만들어 내지 않는다.

## 레퍼런스 카드

문서는 실제 보고서·가이드·편집물의 표지와 대표 본문·표/그림 면까지 조사한다. 다이어그램·인포그래픽은 같은 의미 구조의 실제 사례를 찾고 축·관계선·라벨·출처·범례를 확인한다. 도구 갤러리의 예시는 표현 가능성을 보여줄 뿐 원본 데이터의 정확성을 보증하지 않는다.

가능하면 출처 링크와 확인 날짜, 실제 화면/페이지의 캡처·크롭, 확인한 폭·판형을 묶은 작은 레퍼런스 보드를 만든다. 캡처가 없는 사례는 링크만으로 관찰 가능한 범위를 적는다. 원본 관찰값과 새 결과물에 적용할 토큰·규칙은 따로 기록한다.

레퍼런스가 여러 개인 작업은 **출처 등록부**를 만든다. 각 원본의 URL/파일·버전 또는 확인 날짜·사용한 화면 상태·역할(구조/시각/모션/콘텐츠)·캡처 근거와 현재 결과물의 대응 위치를 연결한다. 라이브 페이지가 나중에 달라질 수 있으므로, 의사결정 당시 캡처를 우선 근거로 보존한다. 원본과 가안이 유사하면 `일반 관례 / 독특한 요소 조합 / 의도적으로 채택 / 우연히 겹침 / 판단 보류`를 구분하고, 독특한 조합이라는 지적에는 원본과 가안의 실제 두 위치를 함께 제시한다. 단일 색·범용 카드·보통의 페이드처럼 널리 쓰이는 요소만으로 모방을 판정하지 않는다. 근거가 없는 항목은 유사·독창성 PASS로 쓰지 않는다.

각 후보에 다음을 제공한다.

- 제품·페이지 이름과 직접 링크, 확인한 화면/기기 및 관찰 범위
- 볼 수 있는 스크린샷·크롭·링크 미리보기 중 가능한 시각 근거
- 배울 원리: 탐색·계층·그리드·밀도·타이포그래피·전환 중 구체적인 사항
- 우리 기능·화면에 적용할 위치와 이유
- 맞지 않는 부분, 적용 시 바꿀 점

최종 시안에 쓰는 이미지 슬롯은 **주제 관련성 / 같은 인물·물건의 전후 동일성 / 놓이는 화면의 시간·상태·행동 맥락**을 각각 확인한다. 검색 결과의 제목이나 썸네일만 맞는 사진, 다른 사람을 같은 사람의 전후 장면처럼 놓은 사진, 작업 상태와 맞지 않는 이미지는 대체하거나 명시적 예시로 격리한다. 슬롯별 출처·크롭·대체 이미지와 실제 렌더를 기록한다.

‘깔끔하다’, ‘세련됐다’만으로 선정하지 않는다. 예를 들어 필터를 결과 옆에 유지해 조건과 결과의 관계를 보이게 하는지, 제목·메타정보의 대비로 스캔 순서를 만드는지 설명한다. 실제 관찰과 예상 효과를 구분한다.

## 사용자와 방향 선택

비슷한 사례를 많이 나열하지 말고 구별되는 2~3개 방향으로 묶어 비교한다. 각 방향의 대표 사례, 정보 밀도, 분위기, 적합한 과업, 선택 비용을 제시한다. 사용자가 좋아하는 부분과 피하려는 부분을 물어보고 선택을 기록한다. 서로 충돌하는 스타일을 설명 없이 혼합하지 않는다.

## 학습과 자산 사용의 경계

레퍼런스를 ‘학습’한다는 것은 화면에서 설계 원리를 분석하고 현재 작업에 반영하는 뜻이다. 모델을 재훈련했다거나 영구적으로 배웠다고 말하지 않는다. 경쟁사의 로고·문구·독특한 화면을 그대로 복제하지 않는다. 이미지·아이콘·폰트의 재사용은 사용 권한과 라이선스를 확인한다. 조사용 캡처를 최종 배포 자산으로 사용하지 않는다.
