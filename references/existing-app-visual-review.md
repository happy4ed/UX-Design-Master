# 기존 앱·웹의 실제 화면 문제 지적 보고서

## 발동 조건과 결과

기존 앱·웹의 디자인, UI, UX, 접근성 또는 일관성을 **검수·진단**해 달라는 요청에 적용한다. 결과는 문제를 실제 화면 위에 표시한 독립 실행형 HTML과 짧은 전달 요약이다. 신규 디자인의 A1→D 승인 절차를 이 진단에 끌어오지 않는다. 사용자가 수정까지 요청했다면 수정 전 보고서와 같은 상태의 수정 후 캡처를 분리해 남긴다.

## 실제 렌더와 좌표 수집

1. 제품의 목적 한두 문장과 검수 대상 범위를 적고 실제 실행 대상에 접근한다. 웹은 대상 브라우저와 뷰포트에서, 네이티브 앱은 대상 기기·에뮬레이터에서 캡처한다. 제공된 스크린샷만 있으면 정적 화면 분석으로 범위를 제한하고 조작 결과를 단정하지 않는다.
2. 대표 과업의 **진입 → 입력/선택 → 결과 → 닫기/뒤로 → 오류·복구**를 따라가며 화면·상태별 PNG를 저장한다. 콘텐츠가 적을 때와 찼을 때, 지원하는 좁은 폭·큰 글자·언어/RTL 등 관련 경계를 포함한다. 다른 상태의 캡처를 현재 상태의 증거로 재사용하지 않는다.
3. 캡처마다 화면 ID, 상태, 기기·뷰포트, 픽셀 크기, 배율/DPR, 캡처 시각, 진입 경로와 조작 순서를 기록한다. 웹 DOM 좌표는 스크린샷 좌표와 다르다. 뷰포트 캡처는 `(DOM x−viewport x)×DPR`, 전체 페이지 캡처는 스크롤 오프셋과 DPR을 적용한다. 기기 프레임을 포함한 이미지라면 프레임 안 화면의 원점도 더한다. 좌표를 바꾼 뒤 원본 PNG 위에 박스를 그려 직접 확인한다.
4. 각 발견은 실제 보이는 문제 영역의 이미지 픽셀 `(x, y, width, height)`에 고정한다. 문제 전체가 화면에 걸치면 사용자가 먼저 봐야 할 요소를 표시하고 관련 상태를 별도 캡처로 추가한다. 관찰, 첫 예상과 실제 결과(조작 문제일 때), 사용자 영향, 심각도, 구체적인 수정 방향, 재확인 조건을 기록한다. 수치 검사 후보는 실제 화면에서 확인한 뒤 문제로 확정한다.
5. 독립 사용자 관점 검수를 마친 뒤 [기능·정보 명세](functional-inventory.md)를 연다. 확정된 필수·부가·조건부 기능과 정보가 실제 화면·상태·과업에 있는지 대조한다. 명세만 있고 화면에서 실행·읽을 수 없는 항목은 해당 캡처의 누락 위치를 표시한다. 원래 기능인지 불확실한 것은 확정 결함이 아니라 확인 필요로 기록한다.
   [동작 중 콘텐츠·행동 밀도 검수](runtime-content-and-actions.md)를 따라 시트·확장·키보드·오류 상태에서 필수 정보의 잘림과 한 줄 조작의 과밀을 확인한다. 초기 화면만 보고 접근 가능성을 추정하지 않는다.
6. 사람·계정·영수증 등 민감한 실제 데이터는 캡처 전에 테스트 계정이나 가림 처리된 상태로 준비한다. 보고서는 기본적으로 로컬 파일이며 외부 게시를 검수 요청만으로 승인받았다고 보지 않는다. 외부 레퍼런스 이미지를 스킬 배포 패키지에 넣지 않는다.

정확한 위치가 없는 일반 미감 평가는 발견 목록에 넣지 말고, 확인할 화면을 추가한다. 증거가 부족하면 `NOT_RUN` 또는 `NOT_TESTABLE`로 표시한다. 문제 없는 화면도 실제 본 범위와 상태를 적고 한 화면의 PASS를 다른 화면으로 전파하지 않는다.

## 단계별 제출과 사용자 피드백

같은 `reportId`로 근거와 추천안의 HTML을 단계별로 제출한다. 실제 수정이 요청·수행된 뒤에만 수정 후 재검증 HTML을 제출한다. 수정 전에는 재검증을 `NOT_RUN`으로 남기고 수정 후 화면을 만들어 내지 않는다. 사용자는 각 단계에서 문제를 클릭해 근거를 확인하고 수용·수정 요청·반려와 의견을 남긴다. 보고서의 의견은 브라우저 로컬 저장소에 보관되며 JSON으로 내보내거나 다음 보고서에서 불러올 수 있다. 다음 단계에서는 전달받은 의견마다 `feedbackResponses[]`에 `findingId/userComment/status/response`를 기록해 **반영·일부 반영·반려·보류와 그 이유**를 해당 문제 상세에 보여 준다. 사용자가 남기지 않은 의견이나 승인 상태를 만들어 넣지 않는다.

| 단계 | 화면에 보여 줄 것 | 다음 단계로 옮길 것 |
| --- | --- | --- |
| `evidence` | 실제 캡처, 문제 위치, 관찰·영향, 미검토 범위 | 사용자의 문제 판정·추가 캡처 요청 |
| `recommendations` | 앞 단계의 근거, 선택 가능한 수정안의 **실제 렌더 PNG·동작 원형·영상**과 각각의 이유·대가 | 사용자가 수용·수정·반려한 안 |
| `verification` | 같은 조건의 수정 전후 캡처, 수정 결과 PASS/FAIL/NOT_RUN, 미해결 문제 | 실제 결과물과 남은 문제 |

추천안은 설명 문장만으로 제출하지 않는다. 시각 수정안은 실제 화면으로 렌더하고, 흐름·모션 수정안은 조작 가능한 원형 또는 영상으로 보여 준다. 보고서 자체에는 펼침·위치 강조·화면 이동의 절제된 모션을 넣고 `prefers-reduced-motion`을 따른다. **보고서 UI가 움직이는 것**을 제품 모션의 검증으로 세지 않는다. React·Tailwind CSS가 이미 있는 프로젝트에서는 그 스택으로 보고서 화면을 제작해도 된다. 단일 파일 전달·오프라인 열기가 필요한 기본 보고서는 외부 CDN 없이 내장 CSS·JavaScript로 같은 조작과 레이아웃 품질을 제공한다.

## HTML 산출물

[주석형 보고서 렌더러](../scripts/render_app_review_report.py)는 실제 캡처 PNG와 JSON 기록을 묶어 한 HTML 파일로 만든다. 화면 위의 번호와 하단 발견 카드의 번호를 연결하고, 클릭·키보드 포커스로 해당 위치를 찾을 수 있게 한다. 카드에는 심각도, 실제 관찰, 사용자 영향, 수정 방향과 재확인 조건이 보인다. 화면별 검토 상태와 미검토 범위가 보고서 앞에 나온다.

```bash
python3 scripts/render_app_review_report.py --input review.json --out review.html
```

입력의 첫 단계 구조는 다음과 같다. `screenshot`은 JSON 파일 기준의 PNG 경로이고 `rect`는 **PNG 원본 픽셀 좌표**다. 화면 ID와 발견 ID는 중복할 수 없다. 단계 페이지끼리는 선택적인 `stageReports`의 `evidence/recommendations/verification` HTML 링크로 연결한다. `recommendations` 단계에는 발견별 `recommendations[]`를 넣고, 각 안에 `id/title/reason/tradeoff`와 `previewScreenshot`(PNG), `motionPreview`(MP4/WebM), `prototypeUrl`(작동 원형) 중 하나 이상을 연결한다. `verification` 단계에는 같은 발견마다 `verificationResult/verificationNote`를 추가한다. `PASS/FAIL` 판정에는 같은 조건의 `afterScreenshot`이 필수다. 수정하지 않은 `NOT_RUN`에는 수정 후 캡처를 요구하지 않는다.

```json
{
  "project": "검수 대상 이름",
  "reportId": "project-review-01",
  "purpose": "사용자가 이 앱에서 하려는 일",
  "reviewedAt": "2026-11-04",
  "stage": "evidence",
  "screens": [
    {"id": "home-entry", "title": "홈 · 첫 진입", "state": "초기", "device": "Android 실기기", "viewport": "390×844 dp", "screenshot": "captures/home-entry.png", "reviewStatus": "REVIEWED", "capturePath": "앱 실행 → 홈"}
  ],
  "findings": [
    {"id": "F-01", "screenId": "home-entry", "severity": "major", "title": "주 행동이 목록 아래에 가려짐", "rect": {"x": 55, "y": 650, "width": 280, "height": 70}, "observed": "첫 진입에서 행동 버튼이 하단 바에 겹친다", "impact": "사용자가 다음 단계를 찾지 못한다", "recommendation": "버튼과 하단 바의 배치를 분리한다", "verify": "같은 기기·큰 글자에서 다시 캡처", "evidence": "캡처의 하단 영역"}
  ],
  "notReviewed": ["로그인이 필요한 결제 화면: 접근 자료 없음"]
}
```

도구는 파일 존재, PNG 크기, 모든 `rect`의 이미지 안쪽 범위, 필수 서술과 화면 연결을 검사한다. 잘못된 좌표·누락된 이미지·빈 근거가 있으면 HTML을 만들지 않고 실패한다. 이는 **기록 검사**이며 문제 발견과 시각 품질 판정을 자동으로 하지 않는다. 생성 뒤 모바일·데스크톱에서 HTML을 직접 열어 핀 위치, 이미지 크롭, 줄바꿈·가로 넘침을 확인한다.
