# 구조와 합의 산출물

## 앱·웹 PRD의 범위

앱·웹에서는 디자인 브리프와 A1 기능 구조, A2 과업 흐름, A3 화면·상태 명세를 **하나의 PRD(제품 요구사항 문서)**로 관리할 수 있다. A1에서 목표 사용자·해결할 문제·제품 목표·범위와 범위 밖·우선순위·성공을 판단할 근거·제약·기능별 수용 조건을 초안으로 적고, A2와 A3에서 실제 흐름과 화면 책임을 연결한다. 수치 목표나 도메인 사실을 모르면 지어내지 않고 `미확인`으로 남긴다. 각 항목에는 `사용자 요청 / 근거 있는 제안 / 확인됨 / 미결정` 출처·상태를 붙인다. 기능 이름만 나열한 자료는 PRD 완료로 표시하지 않고 기능 목록 또는 기능 명세로 부른다. PRD라는 이름이 A1→A2→A3 순서나 단계별 사용자 확인을 합치거나 생략하지 않는다.

**프로젝트 수치 계약:** 창·화면 크기, 한 번에 보일 행 수, 허용 항목 수, 저장 주기, 간격, 색 개수, 모션 시간처럼 제품·과업에 따라 달라지는 값은 공통 규칙으로 고정하지 않는다. 해당 과제에서 `값 또는 범위 / 근거 / 사용자 확정·설계 제안·미확정 / 적용 화면·상태 / 검증할 실제 기기·자료`를 기록한다. 아직 결정할 근거가 없으면 빈 값을 임의 기본값으로 채우지 않고 미확정으로 둔다. 회귀 시험의 숫자는 그 사례의 fixture일 뿐 새 프로젝트의 기본값이 아니다. 공통으로 명시할 하한은 글자 크기·조작 영역 등 접근성 기준에 한정하고 플랫폼의 논리 단위 및 확대 상태에서 다시 확인한다.

## 디자인 브리프

결과물 목적 / 주요 사용자·독자 / 최우선 과업·읽기 목적 / 매체·플랫폼 / 실제 콘텐츠·데이터 / 브랜드·기술·편집 제약 / 납품 형식 / 범위 밖 항목을 간결하게 정리한다. 확인한 사실, 사용자 선택, 제안을 구별한다.

## A1 · 기능 또는 내용 구조표

앱·웹에 적용한다. 문서에는 [문서 디자인](document-design.md)의 주장·근거·장/절·대표 페이지 구조를 사용한다. 발표 자료는 [발표 자료 디자인](presentation-design.md)의 청중·결론·근거 구조와 슬라이드 역할을 붙인다. 다이어그램·인포그래픽은 [의미 유형과 데이터 계약](diagram-infographic.md)을 붙인다.

| 기능 집단 | 사용자 목표 | 기능 | 우선순위 | 진입 화면 | 결과·의존성 |
| --- | --- | --- | --- | --- | --- |

이 표와 함께 [기능·정보 누락 방지 명세](functional-inventory.md)를 **A1 의무 산출물**로 작성한다. 집단의 상하위, 기능의 필수/부가/조건부 구분, 조건이 참·거짓일 때의 행동, 기능별 입력·결과·수용 조건을 ID로 기록한다. 화면에 필요한 정보는 기능과 별도의 `필수 / 부가 / 조건부` 표로 만들고 출처·표시·넘침 규칙과 사용하는 기능을 연결한다. [기능 목록 검사기](../scripts/check_functional_inventory.py)로 누락을 검사한 뒤 사용자에게 필수 여부와 제안 기능을 확인받는다. 아직 정하지 않은 화면 수를 A1에서 확정값으로 채우지 않는다.

목록을 메뉴로 그대로 복사하지 않는다. 과업의 빈도, 순서, 사용자 역할에 따라 묶는다. 검색·필터·설정이 실제 필요한지 검토한다. 핵심 흐름은 시작 → 선택·입력 → 실행 → 결과·복구로 표현하고 뒤로 가기와 중단 후 재개를 고려한다.

핵심 대상(예: 서류·청구 건·예약·주문)이 생기거나 바뀌는 제품은 **대상별 만들기 → 보기 → 수정 → 결과/완료 후 상태**를 A1 필수 기능 대조표로 작성한다. 각 단계에 사용자 과업·현재 대체 통로·기능이 없을 때의 피해·추가 조작 부담·가벼운 대안·요청/제안 출처를 적는다. 사용자에게 없는 기능을 임의 확정하지 않고 누락은 제안으로 올린다. A3나 D에서 빈칸이 드러나면 A1로 돌아가 확인받는다. 단순 목록을 ‘결과 보기’로 채우지 말고 처리 결과의 값·상태·다음 행동이 실제 보이는지 확인한다.

**처리 유형 판정은 A1 필수 절차다.** 자동 인식·추출, 자동 분류, 자동 계산·합산, 추천이 있으면 [처리 유형별 과업 의무](../knowledge/task-obligations.json)를 해당 기능 집단에 대조한다. 빠진 검토·수정 기능은 사용자 요청으로 꾸미지 않고 **제안** 행으로 표시한다. 원본 자료가 없으면 실제 필드·서식은 미확인으로 남기되 원본 대조와 수정 과업은 제안한다. [A1 기록 검사기](../scripts/check_task_obligations.py)로 누락을 경고한다. 검사기 PASS는 기능의 적합성이나 화면 품질 PASS가 아니다.

A1 검사 입력 JSON에는 `processingTypes` ID 배열과 `features`의 `id·source`(`user`/`proposal`)를 기록한다. 없는 필수 기능은 검사기가 제안 문장으로 돌려준다. 제안은 A1 확인을 거쳐 채택하거나 거절하고 이유를 남긴다.

이 표를 사용자와 먼저 확인한다. 화면 이름·개수는 이 단계에서 확정하지 않는다.

## A2 · 사용자 또는 독자 흐름표

| 흐름 ID | 시작 조건 | 선택·입력 | 실행 | 결과·오류·복구 | 뒤로가기·중단 후 복귀 |
| --- | --- | --- | --- | --- | --- |

A1에서 확인한 기능만 연결한다. 주 흐름과 중요한 분기·실패 상태를 사용자에게 보여주고 순서와 결과를 확인받는다. 내용이 추가되면 A1 구조와 우선순위를 먼저 갱신한다. 확정한 **조작 기능 ID마다** 주 흐름 또는 조건부 분기 ID를 붙인다. 빠진 기능·새로 나타난 기능은 [기능 목록 검사](../scripts/check_functional_inventory.py)로 찾고 A1의 필수/부가/조건부 결정으로 되돌아가 정리한다. 조건부 기능은 발동 조건과 비해당 동작을 함께 보여 준다.

사용자 유형마다 **처음 온 이유 / 지금 궁금한 것 / 성공했다고 판단하는 순간**을 실제 자료나 명시적 가정으로 적고, `질문 → 답을 주는 데이터 → 흐름 단계 → 예상 화면/상태`를 연결한다. 화면 하나에 모든 질문을 몰지 않는다. 임의 인물을 사실로 만들지 않으며, 답을 줄 데이터가 없으면 미확인으로 남겨 A2에서 확인한다. B 와이어프레임에서는 질문의 답이 실제 화면에서 읽히는지 검증한다.

## A3 · 화면 분할과 키 프레임 명세

앱·웹의 화면/상태, 문서의 대표 페이지/스프레드 중 구성 원칙이 달라지는 단위를 기록한다.

| ID·화면/상태 | 목적·진입 조건 | 콘텐츠 우선순위 | 기능·주 행동 | 다음 화면·결과 | 예외·반응형 변화 |
| --- | --- | --- | --- | --- | --- |

적용 가능한 상태만 포함한다: 초기, 로딩, 비어 있음, 정상, 선택·편집, 검증 실패, 통신 실패·재시도, 권한 없음, 완료. 인증·결제 등 중요한 동작의 취소·중복 실행도 고려한다. 실제 구현 범위와 시각적으로만 표현하는 부분을 명확히 한다.

A2의 각 흐름 단계가 어느 화면·페이지에 속하는지 표시하고, 합치거나 분리하는 대안을 사용자와 결정한다. 공통 화면 틀과 특정 기능·페이지 전용 영역도 구분한다. 이 확인 전에는 3안 와이어프레임을 제작하지 않는다. 확정한 UI 기능 ID와 필수·부가·조건부 정보 ID를 화면·상태 ID에 연결한다. 조건부 항목은 조건이 보이는 상태가 실제 화면 사용 맵에 있어야 한다. B/C 실제 캡처에서는 명세상 화면에 있는 ID와 **실제로 읽히거나 조작되는 ID**를 따로 적어 누락을 검사한다. D/최종에서는 기능별 실제 실행·결과 근거를 남기며 미실행을 PASS로 바꾸지 않는다.

**와이어프레임에 붙일 키 프레임 계약:** 각 화면·상태 옆에 목적 한 문장과 진입부터 이탈까지의 상태 순서를 적는다. 고르기→처리 중→결과처럼 여러 단계가 있으면 각 상태를 따로 렌더한다. 화면 이름과 첫 장면만 보고 무엇을 하는 화면인지 설명할 수 없는 경우 제시 전에 화면의 정보와 행동 표기를 수정한다.

## 역할·구성 대안 및 와이어프레임 비교

[의미·역할과 대안 설계](semantic-design.md)에 따라 과업→역할→필요 요소→구성 후보를 기록한다. 신규/주요 개편은 GUI 이전에 같은 요구사항을 만족하는 최소 3개의 구조적 와이어프레임 대안을 만든다. 각 안의 초기/포화 조건·핵심 과업·장단점·추천 근거와 실제 화면을 함께 제시한다. 서로 다른 페이지 3장을 대안으로 세지 않는다.

**확인 B·C 제시 전 사용자 관점 리허설:** 실제 렌더에서 (1) 각 화면 목적과 상태 순서가 읽히는가, (2) 같은 결과를 내는 조작이 겹치는가, (3) A1 업무 규칙을 드러내는 경계 자료가 있는가, (4) 여러 열·묶음의 읽기 순서와 정렬을 측정했는가, (5) 숫자가 원본 값인지 계산 값인지 구분되고 식을 볼 수 있는가, (6) 직전 사용자 지적이 다른 화면에도 적용되는가, (7) 명세의 필수·부가·조건부 기능과 정보가 해당 화면·상태에 실제로 있는가를 답한다. 답이 없는 화면은 수정 후 제시한다. [리허설 기록 검사기](../scripts/check_design_preflight.py)는 이 질문별 결과·근거의 존재만 확인하며 실제 사용성의 PASS를 선언하지 않는다.

검사기 입력 JSON은 `stage`(B/C), `screens`의 `id·purpose·stateOrder·renderEvidence`, `rehearsal`의 `screenPurposeAndStateOrder·controlOverlap·businessRuleFixtures·multicolumnOrderAndAlignment·sourceVsComputedValues·priorFeedbackPropagation·functionalInventoryCoverage` 각각의 `result·evidence`를 가진다. C에는 같은 승인 와이어프레임을 적용한 **9개 시각 테마**의 `visualDirections`별 `componentMeasurements·selectionStyleSignature·controlVisualHierarchy·axisMixing·semanticColorExamples·platformConventionCheck`를 추가한다. [9개 테마 기록 검사](../scripts/check_theme_exploration.py)에는 색·여백·R·컴포넌트·재질 등 축별 차이와 실제 렌더 근거를 남긴다. 적용되지 않는 항목은 근거와 함께 `NOT_APPLICABLE`로 기록한다.

**확인 D의 앱·웹·대화형 문서 산출물은 동작하는 프로토타입이다.** [프로토타입 계약](interactive-prototype.md)의 핵심 경로·실제 조작·분기·복구·모션 감소·경계 상태를 실제 화면에서 확인하고 링크와 재현 절차를 함께 제시한다. 제시 전 [D 프로토타입 기록 검사](../scripts/check_prototype_contract.py)로 필수 경로와 검증 근거의 누락을 찾는다. 기록 검사 PASS는 동작이나 사용성 PASS가 아니다.

발표 자료의 확인 D는 실제 장 넘김과 단계 공개를 조작할 수 있는 슬라이드 시안으로 진행한다. 일반 읽기 문서에 조작형 프로토타입을 강제하지 않는다. 발표 자료는 전체 슬라이드의 역할·주장·증거·읽기 순서·미리보기와 내보낸 파일의 검수 기록을 [발표 자료 계약 검사기](../scripts/check_presentation_contract.py)로 점검한다. 기록 PASS는 발표 이해도·시각 품질 PASS가 아니다.

## 확인 요청 형식

먼저 표·화면·프로토타입을 보여준다. 다음으로 결정이 필요한 차이와 권장안을 짧게 설명한다. 마지막에 답변하기 쉬운 확인 질문을 묶는다. ‘진행할까요?’만 묻지 않는다.

- A1: 기능 또는 콘텐츠 누락·과잉·우선순위
- A2: 행동 또는 읽기 순서·분기·결과·복구
- A3: 화면·상태 또는 장·절·대표 페이지의 합침/분리와 역할·공통/전용 요소
- B: 최소 3개 와이어프레임과 비교·추천 이유 / 사용자 선택·수정 / 정보·읽기 순서·행동·탐색·매체별 구성
- C: 승인 구조의 9개 테마 실제 화면 / 색상·여백·R·컴포넌트·재질·폰트 축 비교 / 선택·조합안의 재렌더
- D: 조작 가능한 프로토타입으로 핵심 경로·분기·복구를 시연하고 모션 적용 대상·강도·느낌과 정적 대안 확인

최종 구현 중 작은 간격 조정과 오류 수정마다 다시 승인받지 않는다. 승인된 구조·주요 기능·시각 방향이 바뀌는 경우에만 영향받는 결정을 다시 확인한다.

## 진행 문서 최소 필드

현재 단계, 브리프, 기능 구조, 흐름, 화면 분할·프레임 명세, 레퍼런스 링크와 적용 근거, A1/A2/A3/B/C/D별 사용자 답변과 승인 범위, 토큰·모션 결정, [지식 적용 표](knowledge-application.md), 미결정 사항, 검수 결과, 다음 작업. 사용자 답변 없이 승인으로 표시하지 않는다.
