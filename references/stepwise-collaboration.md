# 사용자와 단계별로 디자인 명세 구체화

신규 디자인과 큰 개편의 핵심은 완성안을 한 번에 제시하는 일이 아니라, **사용자가 결정할 수 있는 크기로 명세를 나누어 확정**하는 것이다. 앱·웹은 A1 기능 구조 → A2 사용자 흐름 → A3 화면 분할 → B 와이어프레임 3안 → C 시각 시스템 → D 모션 순서다. 앱·웹의 A1~A3는 [PRD 초안과 확정 범위](design-contract.md#앱웹-prd의-범위)를 단계별로 채우는 과정이며, PRD라는 문서 이름이 확인 단계를 합치지 않는다. 문서는 기능 대신 주장·내용 구조, 사용자 흐름 대신 독자의 읽기·탐색 경로, 화면 분할 대신 장·절·대표 페이지를 쓴다.

| 확인 | 사용자에게 보여줄 실제 산출물 | 결정받는 내용 | 확정 전 다루지 않을 것 |
| --- | --- | --- | --- |
| A1 기능·내용 구조 | 목표·기능 집단·개별 기능·우선순위·공통 기능 표, 자동 처리 유형의 검토·수정 기능 제안 또는 문서 주장·근거 표 | 누락, 과잉, 범위와 우선순위 | 화면 수, 배치, 색 |
| A2 흐름 | 시작·선택/입력·실행·결과·오류/복구·뒤로가기 경로와 분기 그림 | 행동 순서, 주요 분기와 복귀 | 기능 추가를 묵시적으로 확정, 화면 분할 고정 |
| A3 화면·페이지 분할 | 흐름의 각 단계가 들어갈 화면·상태 또는 장·절·대표 페이지, 목적 문장·진입→이탈 상태 순서, 합침/분리 후보 | 경계, 키 프레임 역할, 공통·전용 요소 | 최종 배치와 GUI |
| B 와이어프레임 | 같은 요구사항의 구조적으로 다른 3안과 초기/포화·업무 규칙 경계, 제시 전 사용자 관점 리허설 | 정보 우선순위, 구성과 탐색 | 색·폰트 확정 |
| C 시각 시스템 | 선택된 구성의 축별 시각 방향, 방향별 컴포넌트 실측표, 의미 색·테마 전환 화면, 제시 전 리허설 | 구성·컴포넌트·색·밀도 축과 토큰 | 미승인 모션 적용 |
| D 모션 | 변화 목록, 정적 대안, 실제 재생 비교. 인터랙션·흐름이 있는 매체는 스크롤·조작·화면 이동·상태 변화가 작동하는 프로토타입과 핵심 경로 시연 | 적용 대상·강도·느낌과 흐름의 이해 가능성 | 미검증 동작의 완료 선언 |

각 단계에서는 **현재 결정할 표나 화면과 수정 가능한 선택지**를 먼저 보여준다. 사용자의 답변을 기록하고 변경된 행·흐름·화면을 갱신한 뒤 다음 단계로 간다. 사용자가 제안을 거부하면 그 이유를 명세에 반영한다. 한 번에 모든 결정을 묻거나, 여러 단계를 먼저 완성해 사용자가 이미 만들어진 결과만 고치게 하지 않는다. 사용자가 명시적으로 묶음 검토·위임을 요청했다면 그 범위에서만 합친다. 기존에 확인된 결정은 다시 묻지 않는다.

결정이 바뀌면 그 아래 단계의 영향 범위를 추적한다. A1 기능이 바뀌면 A2 흐름을, A2 경로가 바뀌면 A3 화면 경계를, A3가 바뀌면 B 와이어프레임을 다시 확인한다. 영향이 없는 상위 단계 전체를 처음부터 재승인받지 않는다. 필수 확인을 기다리는 동안 관련 레퍼런스·실제 콘텐츠·기술 제약 조사처럼 독립적인 작업을 이어간다.

진행 기록에는 `제안 / 사용자 수정 / 확인됨 / 미결정`을 구분하고, 확인된 날짜·답변·영향받은 다음 산출물을 적는다. 도구 실행 성공이나 침묵을 확인으로 기록하지 않는다.
