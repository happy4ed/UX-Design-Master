# 독립 사용자 관점 검수

## 역할과 발동 시점

앱·웹·대화형 문서의 와이어프레임(B), 시각 방향(C), 조작형 프로토타입(D), 최종 결과물과 일반 문서의 대표 페이지(B/C)·최종 파일에는 **제작자가 아닌 별도 에이전트**의 검수를 붙인다. 좁은 수정은 변경된 화면·페이지와 그에 연결된 전후 상태만 검토한다. 이 검수는 제작자의 렌더 실측·접근성 검사와 별개다. 자동 검사 PASS나 제작자의 자기 평가로 대체하지 않는다.

제작자는 검수 전에 실제 열리는 URL/파일, 대표 진입점, 필요한 상태를 준비한다. 별도 에이전트에는 아래 **봉인된 입력**만 전달한다.

| 전달 | 범위 |
| --- | --- |
| 목적 | 대상 사용자가 하려는 일을 한두 문장으로만 설명 |
| 대상 | 앱/웹/문서, 독자·사용자, 지원 기기·판형 |
| 산출물 | 실제 렌더 URL·이미지·PDF·프로토타입 진입점과 접근 방법 |
| 검수 단계 | B/C는 아직 동작 검증이 불가능한 정적 시안인지, D/최종은 실행 가능한지 표시 |

기능 목록, 컴포넌트 명세, 화면별 정답, 기존 지적, 수정 예정안, 합격을 유도하는 설명은 먼저 주지 않는다. 평가자가 제작 채팅이나 설계 문서를 읽지 않게 별도 대화 문맥에서 시작한다. 로그인·테스트 데이터가 필요한 경우 접근용 자료만 제공하고 기능을 설명하지 않는다. 제품의 핵심 도메인 지식이 없으면 추측한 요구사항을 결함으로 단정하지 않는다.

Claude Code에서 `ux-design-independent-reviewer`가 등록돼 있으면 **새 subagent**로 지정해 위 봉인 입력만 전달한다. 이 저장소에는 `.claude/agents/ux-design-independent-reviewer.md`를 제공하며 제작 대화와 프로젝트 지침을 상속하지 않도록 설정했다. 스킬만 다른 환경에 올려 에이전트가 등록되지 않았으면 새 일반 Agent에 [내부 평가자 프롬프트](../agents/independent-design-reviewer.md)의 본문과 봉인 입력만 전달한다. 그 환경에서 프로젝트 지침 등 제작 맥락이 자동 주입되는지 확인하고, 차단할 수 없으면 검수의 독립성 제한을 보고한다. 별도 에이전트를 실행할 수 없으면 `NOT_RUN`으로 기록하고 제작자 자체 검수로 대체하지 않는다. 평가자에게 편집 권한이나 수정 업무를 주지 않는다.

## 평가 절차

1. 목적과 산출물만 보고 각 화면·페이지가 무슨 일을 하는지, 주요 조작을 누르면 무엇이 일어날지 **먼저 예상**해 기록한다. 그 뒤 실제 제목·문구·화면을 읽고 예상과 다른 지점을 찾는다.
2. B/C 정적 시안은 보이는 의미·명칭·정보 위계·컴포넌트 역할 후보를 평가하고, 실제 동작은 `NOT_TESTABLE`로 둔다. D/최종에서는 첫 진입부터 주요 과업을 직접 눌러 끝·오류·복구까지 확인한다. 문서는 첫 페이지→목차/제목→본문/표/그림→결론·출처의 읽기 경로를 따른다.
3. 초기·포화 내용, 좁은 폭과 대표 폭, 글자 확대를 본다. 잘리거나 말줄임 때문에 **필요한 뜻을 알 수 없는** 사례를 찾고, 의도된 요약과 구별한다.
4. 아래 판정 질문을 모든 화면·대표 페이지와 주요 행동에 적용한다. 발견 없음을 적을 때도 실제 확인 범위를 남긴다.

확인 C에서 여러 테마를 비교하는 중에는 각 후보의 고유한 시각 문법이 실제 렌더에서 구별되는지, 색만 바뀐 반복안이 아닌지 비교한다. 사용자가 테마를 고른 뒤 완성한 결과물에서는 화면·상태를 넘나들며 같은 역할의 컴포넌트, 글꼴, 표면, 간격, R/형상이 일관되는지와 강한 재질 효과가 읽기·조작을 방해하는지 본다. 평가자에게 선택한 테마의 명세를 먼저 주지 않는다. 선택안과의 정확한 이월은 제작자가 별도 검사한다.

| 판정 질문 | 관찰 근거 |
| --- | --- |
| 화면·페이지 이름과 기능명이 처음 보는 사람에게 뜻을 전달하는가 | 이름만 보고 예상한 일과 실제 결과가 일치하는지 |
| 주 행동·상태·다음 단계가 설명 없이 발견되는가 | 찾은 경로, 망설인 지점, 누른 뒤의 상태 |
| 정보가 잘리거나 가려져 판단에 필요한 뜻이 사라지는가 | 실제 문구, 폭·확대 상태, 가린 요소 |
| 컴포넌트의 형태와 의미 역할이 맞는가 | tab/필터/switch/버튼/링크/선택 행 등의 예상과 실제 변화 |
| 각 조작이 알맞은 결과를 내고 부적절한 입력을 받지 않는가 | 클릭·키보드·터치의 전후 상태, 뜻밖의 토글·드래그·호버 전용 행동 |
| 반복 요소의 모양·상태·간격·명칭이 같은 역할에 일관되는가 | 같은 역할의 두 위치와 다른 표현의 실제 차이 |
| 중복 문구·라벨·설명이 이해를 돕는가, 방해하는가 | 하나를 가렸을 때 사라지는 정보 또는 남는 오해 |
| 메타포만으로 기능을 정확히 예상할 수 있는가 | 아이콘·형태만 본 첫 예상, 명칭을 가린 사용, 실제 결과. 문화권·접근성에 따라 뜻이 불분명하면 라벨을 유지 |
| 문서·인포그래픽의 읽기 순서와 캡션·범례가 주장과 자료를 연결하는가 | 독자가 도달한 결론과 원본 수치·단위·출처의 연결 |

단순히 라벨 수를 줄이거나 모든 아이콘에 라벨을 붙이라는 규칙으로 판정하지 않는다. 자명한 중복 설명은 제거 후보이지만, 접근성 이름·법적 고지·모호한 아이콘의 라벨은 역할이 있다. 컴포넌트 오류도 외형만으로 단정하지 말고 실제 상태 변화와 영향 대상을 근거로 지적한다.

## 결과와 제작자의 후속 조치

평가자는 `위치·상태·기기/판형 / 첫 예상 / 실제 관찰 / 사용자 영향 / 심각도(차단·중요·다듬기) / 수정 방향 / 근거 화면·단계`를 보고한다. 화면·과업별 `PASS / FAIL / NOT_TESTABLE / NOT_RUN` 범위를 적고, 잘 된 부분도 근거와 함께 남긴다. 점수 하나로 합격시키지 않는다. 보지 못한 화면이나 조작을 통과로 쓰지 않는다.

제작자는 평가 뒤에야 승인된 기능·명세를 열어 발견 사항의 오탐을 가린다. 실제 사용자가 같은 오해를 할 가능성이 있는 항목은 수정하고 같은 **최소 입력**으로 새 에이전트 실행 또는 기억이 없는 새 세션에서 재검수한다. 같은 평가자에게 정답과 수정 의도를 설명한 뒤 재검수시키지 않는다. B/C/D 제시 전의 차단·중요 문제는 고치거나 이유를 적고 해당 단계의 사용자 확인을 받는다. 최종 결과물은 미해결 문제와 영향 범위를 함께 전달한다. 독립 검수의 `PASS`도 사용자의 승인이나 실제 렌더 품질 검수를 대신하지 않는다.
