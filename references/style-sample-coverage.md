# 스타일 샘플의 컴포넌트 범위

스타일 후보를 비교할 때 포스터나 카드 한 장만 그리지 않는다. **같은 기능·문구·데이터**로 스타일별 시연을 만들고, 해당 제품/문서에 쓰일 컴포넌트 계열을 고르게 담는다. 먼저 화면별 컴포넌트 사용 맵을 만든 뒤 샘플 범위를 정한다. 존재하지 않는 기능을 테스트용 샘플에 넣었다면 제품 기능과 분리해 표시한다.

## 범위 표

앱·웹 기준은 다음 계열을 점검한다. 각 계열은 한 화면에 모두 밀어 넣지 않아도 된다. 기준 과업 화면과 별도 컴포넌트 보드로 나눌 수 있다. 빠진 계열에는 이 제품에서 불필요한 이유를 적는다.

| 계열 | 대표 부품 | 비교할 차이 |
|---|---|---|
| 탐색 | 앱바, 탭, 아래 내비, 뒤로 | 현재 위치·선택·뒤로·넓은 화면 재배치 |
| 행동 | 주/보조/글자/아이콘 버튼 | 위계, 모양, 아이콘, 눌림·비활성·포커스 |
| 입력 | 텍스트/검색, 체크, 라디오, 스위치, 슬라이더 | 한 줄/여러 줄, 선택, 값, 끌기·키보드 |
| 정보 | 1/2/3줄 목록, 카드/행, 표/차트, 이미지 | 위아래 여백, 정렬, 길이·포화 |
| 피드백 | 진행, 토스트/스낵바, 성공/주의/오류 | 의미 색·기호·문구·모션 |
| 임시 화면 | 대화상자, 시트, 메뉴 | 열기/닫기, 초점·스크롤 복귀, 버튼 수 |
| 경계 | 빈 상태, 로딩, 오류, 최대 입력 | 다음 행동, 복구, 줄바꿈·잘림 |

문서는 제목·본문·강조·목록·표·차트·이미지·캡션·각주·콜아웃·페이지 넘김을 제품 목적에 맞춰 고른다. 인포그래픽은 노드·연결선·라벨·범례·긴 문구·축소 삽입 크기까지 본다.

## 제출 계약

1. **범위 매트릭스:** `계열 | 대표 인스턴스 | 샘플 위치 | 기본/선택/비활성/포커스/오류 등 필요한 상태 | 근거 등급 | 빠진 이유`를 먼저 적는다.
2. **같은 기준 화면:** 스타일만 바꾼 비교판은 콘텐츠와 과업이 같아야 한다. 컴포넌트 보드도 같은 인스턴스와 데이터를 쓴다.
3. **형태 차이:** 색·R만 다르게 보이면 충분하지 않다. 글꼴·아이콘·패딩·행 간격·슬라이더 해부·표면·상태와 모션의 차이를 가이드 값과 대조한다. 입력은 평면/음각/양각 중 무엇인지, 행동은 누를 때 무엇이 변하는지, 카드와 반복 행은 어떤 Z층인지, 선택·해제는 색 이외에 어떤 표지가 있는지, 스크롤바는 그 스타일의 표면에 맞는지 기록한다. 같은 모양을 재사용한 부품은 공통 플랫폼 관례인지, 근거 부족에 따른 임시 가설인지 적는다.
4. **동작:** 탭·칩·체크·스위치·슬라이더·시트·대화상자·토스트처럼 보이는 상호작용은 실제로 누르거나 끌 수 있게 만든다.
5. **검사:** 각 스타일의 폰/폴드 × 라이트/다크에서 잘림·가로 넘침·글자·조작 범위·상태 변화와 실제 스크롤을 잰다. 기본·선택·해제·누름·포커스의 렌더를 확인하고 원본 부품이 있으면 같은 상태의 원본과 비교한다. 모션 느낌은 실제 전후 프레임을 본다. 완성도가 부족한 계열은 원본 사실 미확인과 임시 구현 추정을 나눠 보여준다. 내부 시연에서 스타일 간 CSS 차이가 확인돼도 원본 일치 판정으로 바꾸지 않는다.

현재 내부 예시는 [미디어 기준 화면](../samples/style-book-reference-screen.html)과 [컴포넌트 시연](../samples/style-book-component-board.html)이다. 후자는 13개 역할 묶음을 보여 주며, 실서비스 원본을 그대로 재현한 증거는 아니다. [브라우저 시험](../tests/test_style_component_board.py)은 19개 스타일의 범위·조작·기하를 검사한다.
