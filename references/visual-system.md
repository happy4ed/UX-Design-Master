# 시각 시스템과 모션

## 잘 만든 제품에서 원리 가져오기

스타일을 입히기 전에 콘텐츠의 중요도와 사용자 행동을 기준으로 시각적 무게를 배분한다. 모든 영역을 같은 카드, 같은 크기, 같은 간격으로 처리하지 않는다. 반대로 다양성 자체를 목적으로 비대칭과 장식을 추가하지 않는다.

제품과 근거 없이 붙이는 대형 히어로, 그라데이션, 유리 효과, 무의미한 대시보드 수치, 과도한 둥근 모서리, 이모지 아이콘, 빈 마케팅 문구는 검토 대상이다. 이 요소들을 일괄 금지하지 않고 실제 기능·브랜드에 필요한지 판단한다. 유행의 대체품을 자동으로 적용하지 않는다.

## 컬러와 타이포그래피

- 프로젝트 기본 팔레트는 배경·본문·표면/경계·주 강조·보조 강조·상태 등 실제 필요한 역할에서 정한다. 색의 개수를 공통값으로 고정하지 않고 제품의 정보 구분과 브랜드 목적에 맞춰 선택한다. 중립색의 명도 단계만 늘려 색 개수를 채우거나 의미 없는 장식색을 추가하지 않는다.
- 팔레트를 제시할 때 색상값과 함께 역할·사용 비율·조합 예시를 실제 대표 화면에 적용한다. **키 컬러를 확정하면 의미 색 체계를 반드시 만든다.** 기본 강조·주의·오류·완료·진행/대기 역할을 프로젝트에 맞춰 정의하고, 상태색과 데이터 색을 기본 브랜드 팔레트와 구분한다.
- 배경/표면/경계/본문/보조/강조/상태를 의미 기반 토큰으로 만든다. 장식색과 동작색을 구분하고 색만으로 상태를 전달하지 않는다.
- 레퍼런스 색상과 그라데이션은 [색상 KG](color-knowledge-graph.md)에서 출처·관찰값·내부 시연값을 구분해 찾는다. 이미지 팔레트의 어두운→밝은 순서를 UI 역할로 자동 매핑하지 않는다.
- 색상 분석과 시각 방향 비교에는 [화면 바탕과 Z 레이어 분석](background-depth-analysis.md)을 적용한다. 화면 전체 바탕과 각 영역·컴포넌트 바탕을 구분하고, 층별 강조색·경계·그림자·블러 및 실제 가림 관계를 기록한다. 효과가 없는 후보도 비교하고 캡처에서 측정할 수 없는 수치를 꾸며내지 않는다.
- 본문은 WCAG AA 대비 4.5:1, 큰 텍스트는 3:1을 기준으로 확인한다. 필수 UI 경계·상태도 적절한 대비를 확보한다. 실제 측정 없이 준수한다고 선언하지 않는다.
- 폰트 후보는 실제 제목·버튼·한글 장문·숫자·영문이 섞인 화면으로 비교한다. 한글 지원, 필요한 굵기, 라이선스, 웹폰트 용량, 폴백의 폭 차이를 확인한다. 가변 폰트 여부와 실제 제공되는 굵기를 확인해 가짜 굵기를 피한다.
- 표시 크기만큼 줄높이·행 길이·자간·숫자 정렬을 설계한다. 좁은 폭의 한글 단어·조사와 혼합 텍스트 줄바꿈을 확인한다. 잘림과 말줄임은 전체 내용을 볼 수 있는 방법과 함께 정한다.
- 화면마다 제목의 **최대 글자 크기**를 정하고 실제 콘텐츠 길이로 검증한다. 이 스킬의 실험 페이지 기본값은 데스크톱 42px, 모바일 30px 상한이다. 다른 제품에 그대로 강제할 숫자는 아니며 브랜드·매체에 따라 정하되 제목이 화면의 과업 정보와 조작부를 밀어내지 않게 한다. 본문과 카드 제목은 제목 상한과 별도 계층을 둔다.
- 도표가 좁은 화면에 들어가지 않으면 글자를 계속 축소하지 않는다. 내부 스크롤, 수직 재배치, 단계 분리, 전체 문구 범례 중 의미에 맞는 방법을 선택한다. 실제 표시 크기에서 글자를 읽을 수 있는지 확인한다.
- 그림·차트는 [그림 삽입 규칙](diagram-infographic.md#그림-삽입-규칙)에 따라 원본 크기와 표시 폭을 분리하고 기본 확대를 1.25배 이내로 제한한다. 부모 글꼴과 승인된 색을 적용하며, 본문에 끼워 넣은 뒤 320·360px과 최종 판형에서 글자·화살표를 다시 본다.

### 의미 색의 다섯 층과 데이터 부호

각 상태 역할에 (a) 글자색과 실제 바탕의 대비 4.5:1 이상, (b) 막대·점과 바탕의 대비 3:1 이상, (c) 옅은 면 및 그 위 글자의 대비 4.5:1 이상, (d) 다크 모드의 같은 층, (e) 색과 함께 붙는 기호·글자 대안을 둔다. 키 컬러의 OKLCH 명도를 기준으로 색상각을 확장하되, 실제 대비를 맞추기 위해 명도 보정이 필요하면 값을 기록한다. 진행·대기는 키 컬러 색상각을 유지하고 채도를 낮춰 구분할 수 있다. 색상만으로 상태를 전달하지 않는다.

관련 데이터는 같은 색상의 명도 차, 다른 범주는 비슷한 명도의 다른 색상각, 순서는 명도 단계, 진행·추세는 목적에 맞는 톤 그라데이션으로 부호화한다. 키 컬러의 보색이 주의색 등 상태 역할과 겹치거나 상태끼리 색상각 차이가 30° 미만이면 기호·레이블로 충분히 구별되는지 확인한다. [색상 KG](color-knowledge-graph.md)를 사용해 변주를 만들고, 실제 대표 화면에 상태 5종과 데이터 예시를 함께 렌더한다. [의미 색 입력 예시](../knowledge/semantic-color-example.json)의 `keyColor·canvas·states·dataEncoding` 구조로 [의미 색 기록 검사기](../scripts/check_semantic_colors.py)를 실행한다. 검사기는 역할·층·대비·색상각·다크 값 누락을 경고한다. 기록 PASS는 렌더의 시각 품질 PASS가 아니다.

## 레이아웃·컴포넌트·자산

문서는 표지·본문·데이터 면에 같은 제목 계층·그리드·캡션 규칙을 적용하되 용도에 따라 밀도를 달리한다. 인포그래픽과 다이어그램은 결과물의 글꼴·색 역할·정렬선·여백 체계에 맞추고, 축·선·면적이 뜻하는 데이터 관계를 스타일로 왜곡하지 않는다. 실제 출력 크기에서 라벨과 출처가 읽히는지 확인한다.

컨테이너, 열, 간격, 패딩, 반응형 전환, 레이어 순서를 정의한다. 자산의 투명 여백과 시각 중심을 확인해 숫자상 중앙 정렬만 믿지 않는다. 아이콘의 굵기·광학 크기, 로고 여백, 사진의 초점과 크롭, SVG viewBox, 이미지 해상도와 비율을 맞춘다. 외부 폰트·이미지가 늦게 로딩되거나 실패해도 영역이 무너지지 않게 한다.

상호작용 컴포넌트의 기본·호버·포커스·눌림·선택·비활성·로딩·오류 상태를 필요한 범위에서 정의한다. 링크와 버튼, 토글과 단발 행동의 의미를 혼동하지 않는다. 이미지와 아이콘은 장식/의미 전달을 구분해 대체 텍스트를 정한다.

## 모션 명세

컴포넌트별 필요성 판정과 사용자 확인 D는 [컴포넌트 모션 판단과 합의](component-motion.md)를 따른다. 화면에서 쓰는 모든 컴포넌트를 대상으로 변화 목록과 정적 피드백을 확인한다. 실제 재생 시안을 보고 대상·강도·이징의 느낌을 각각 선택받는다. CSS·React·네이티브 구현 방식은 같은 상태 계약을 공유하되 매체에 맞게 구현한다.

| 트리거·목적 | 대상 | 시작→종료 | 시간·이징 | 중단·재실행 | 모션 감소 대안 |
| --- | --- | --- | --- | --- | --- |

전환의 목적이 상태 이해·행동 피드백·위치 관계 중 무엇인지 설명한다. 대표 흐름에서 속도와 타이밍을 확인하고 사용자 선호가 있으면 조정한다. 모션 때문에 버튼 작동이나 콘텐츠 접근을 지연시키지 않는다. 레이아웃 측정을 반복하는 효과를 줄이고 가능한 경우 transform/opacity를 사용한다. prefers-reduced-motion과 필요 시 모션 제거 대안을 제공한다. CSS와 애니메이션 키프레임은 구조 단계의 키 프레임과 구분한다.

웹·앱 미리보기와 HTML 문서는 내부 [DOM 모션 컨트롤러](../assets/layout/motion-controller.mjs)를 기본 예제로 쓸 수 있다. TypeScript 프로젝트는 함께 있는 `motion-controller.d.mts` 선언을 사용하고, React 화면에서는 요소가 마운트된 뒤 컨트롤러를 만들고 언마운트 때 `stop()`으로 정리한다. Web Animations API로 모드 변경·재생·일시정지·재시작을 명시하고, 실제 보이는 대상의 위치·투명도·크기 변화를 두 시점의 렌더로 검증한다. SVG의 CSS 키프레임도 같은 검증을 거친다. 재생 대상이 없거나 한 번만 나타나 사용자가 놓치는 효과를 ‘동작’으로 보고하지 않는다. 기기의 모션 감소 설정은 기본으로 존중하되, 사용자가 점검 화면에서 직접 재생을 선택했다면 그 선택을 표시하고 시험할 수 있게 한다.
