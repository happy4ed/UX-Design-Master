# 시각 방향 탐색: 구조 확인 이후

이 단계는 **확인 B에서 구조 와이어프레임을 선택한 뒤** 수행한다. 외부 사례의 장점은 실제로 본 레퍼런스, 빠른 시각 후보, 반복 외형 점검, 브라우저에서의 실렌더 확인이다. 구조 대안을 색만 바꾼 판으로 대체하거나 미확인 기능을 장식으로 덮지 않는다.

시각 방향에 앞서 화면·슬라이드·페이지가 주로 **설득(결정·행동), 조작(과업 완료), 읽기(이해·검색), 경험(작품·장면 감상)** 중 무엇을 돕는지 기록한다. 이는 제품 전체의 단일 성격이 아니라 해당 면의 목적이다. 같은 서비스의 랜딩과 설정 화면, 같은 보고서의 표지와 데이터 면은 다른 강도의 시각 표현을 가질 수 있다. 설득·경험에는 표현을 허용하되 근거와 행동을 가리지 않고, 조작·읽기에는 탐색·판독·플랫폼 관례를 우선한다. 실제 브리프와 사용자의 선택이 이 기본 판단보다 우선한다.

사용자가 특정 레퍼런스를 지정했다면 [레퍼런스 조사](reference-research.md#사용자가-특정-레퍼런스를-말한-경우-조사부터-시작)의 원본 열람·스타일 명세를 먼저 확인한다. 승인된 와이어프레임에 그 명세를 적용한 가안을 **같은 콘텐츠·화면 크기·상태**의 원본과 병렬 렌더하고, `원본 관찰 → 가안 실측 → 차이 → 채택/수정/의도적 변경` 표를 채워 반복 수정한다. 이 비교가 끝나기 전에는 레퍼런스 기반 시각 방향을 확정 후보로 제시하지 않는다.

## 후보를 만드는 세 관점

1. **기존 맥락**: 승인된 브랜드, 사용자 제공 자산, 코드의 토큰·컴포넌트, 앞선 결정에서 출발한다.
2. **실제 레퍼런스**: 같은 매체와 읽기/사용 과업의 사례를 직접 열고, 화면·페이지·상태와 확인 날짜를 기록한다. 가능하면 작은 레퍼런스 보드에 화면 크롭, 출처, 빌려올 규칙(그리드·타입 비율·색 역할·이미지/텍스트 관계)을 함께 둔다. 썸네일만 본 항목은 그 수준으로 표시한다.
3. **탐색 후보**: 의도적으로 다른 정보 밀도·타이포그래피·표면 구분·정렬 체계를 시도한다. 무작위 스타일 이름이 실제 과업과 콘텐츠를 지배하게 하지 않는다.

작은 썸네일·부분 시연으로 폭넓게 탐색해도 된다. 확인 C에서는 [9개 테마 탐색 계약](theme-exploration.md)에 따라 **같은 승인 구조·같은 콘텐츠·같은 데이터 조건**을 가진 9개 시각 방향을 실제 대표 화면으로 렌더해 보여준다. 안정적 사용형, 표현형, 실험형을 함께 포함한다. 색만 바꾸지 말고 유형별 제목/본문의 무게, 정렬선, 여백 소유, 이미지와 내용 관계, 카드/선/배경 구획 선택을 함께 바꾼다. 사용자는 좋아하는 방향의 일부를 조합할 수 있다. 강한 플랫폼·브랜드 제약으로 특정 스타일이 맞지 않으면 그 원형을 다른 시각 문법으로 대체하고 이유를 적는다.

## 확인 C의 축별 선택과 방향별 실측 계약

확인 C에서는 각 안을 통째로 고르도록 묶지 않는다. 승인된 정보 구조를 유지한 채 **구성 계열(선·행/묶음 면/크게 읽기 등), 컴포넌트 스타일, 색 테마, 밀도, 여백, R/형상, 재질**을 별도 축으로 보여주고, 사용자가 축마다 선택하거나 조합할 수 있게 한다. 같은 화면에 색 또는 한 축의 변수값만 바꾼 안은 별도 방향으로 세지 않는다. 방향마다 버튼 모양·높이·R, 목록 행 높이·안쪽 여백, 묶음 간격, 글꼴 운용, 표면·경계 처리가 실제로 달라야 한다. 이 값은 설명 문구가 아니라 렌더에서 측정한 명세표로 제시한다.

방향별 타이포그래피 명세표에는 실제 표시 최소 글자 크기(앱 기본 후보 14, 웹 기본 13 CSS px, 인쇄 문서 6.5pt), 그 크기로 표시되는 실제 문구, 예외 위치와 확대 경로를 적어 **확인 C에서 사용자에게 확정받는다**. 앱은 [실제 기기 글자 크기 실측](app-type-size-calibration.md)으로 물리 보정 상태와 읽기 평가를 함께 보여준다. 기본 크기와 큰 글자·200% 확대의 대표 화면을 함께 보여주고, 확대 시 열·행 높이·줄바꿈·스크롤이 어떻게 재배치되는지도 명세한다. 승인 전에는 작은 글자로 억지로 맞춘 시안을 확정하지 않는다.

| 방향 ID | 버튼 모양·높이·R | 행 높이·inset·묶음 gap | 제목·본문·숫자 글꼴 운용 | 표면·경계·그림자 | 선택 표시 서명 | 실제 측정 화면 |
| --- | --- | --- | --- | --- | --- | --- |

한 방향 안에서는 선택 상태를 나타내는 **기본 시각 규칙 하나**를 정한다. 단계 거르기·보기 전환·목록·칸 선택의 계산 스타일 서명(배경·글자색·굵기·장식·그림자)을 비교하고, 의미나 플랫폼 관례 때문에 다른 규칙이 필요하면 그 이유와 범위를 적는다. 의도하지 않은 검은 버튼이나 solid/outline/shadow 혼용은 수정한다. 조작 무게는 1차 탐색 > 거르기 > 보기·정렬 순으로 둔다. 보기·정렬이 1차 탭처럼 커지면 글자 토글·열 머리 정렬·작은 메뉴 등 같은 역할의 대안을 시험한다.

색 테마는 고정된 구성·컴포넌트·콘텐츠 위에서 프로젝트의 배경·표면·글자·강조·상태 역할을 비교할 수 있을 만큼 키 컬러 후보를 변주해 보여준다. 후보 개수는 제품 목적과 사용자가 결정하며 공통값으로 고정하지 않는다. [색상 KG](color-knowledge-graph.md)에서 같은 OKLCH 명도의 색상각 변주와 보색·유사색·채도 변주를 구분해 사용하고, 각 후보의 실제 화면 및 라이트·다크를 [내부 테마 전환 미리보기](../samples/theme-switcher/index.html) 또는 동일한 기능의 프로젝트 화면으로 전환해 확인한다. 휴대폰 크기 iframe과 PC 크기 보기 링크를 제공한다. 색만 바꾼 화면은 방향 수에 넣지 않고 색 축의 후보로 표시한다.

후보별로 도메인과 콘텐츠에 맞는 정서적 온도(따뜻함/차가움)와 선택 이유를 기록한다. 온도만 다른 후보도 같은 화면·데이터·구성에서 전환해 비교한다. 한국 서비스 팔레트나 회색 바탕·흰 카드 조합을 기본 정답으로 두지 않고, 선택한 키 컬러에서 의미 색·대비·Z 층을 다시 계산한다.

웹 레퍼런스의 구조군을 앱이나 앱 같은 웹에 적용할 때는 [플랫폼 관례 표](mobile-app-study.md#플랫폼-관례와-관찰된-부재)를 먼저 대조한다. 선택한 플랫폼의 원본 화면에서 앱바와 본문 사이에 선·그림자가 없었다면 웹 구조군의 경계선을 그대로 가져오지 않는다. 다른 화면이나 플랫폼까지 같은 관례라고 일반화하지 않고 근거 화면·상태를 기록한다.

## 구체적인 비교 카드

| 항목 | 기록할 내용 |
| --- | --- |
| 출처 | 원본 링크·상태·날짜·스크린샷 또는 페이지 근거 |
| 구조 고정 | 확인 B에서 선택한 와이어프레임 ID·대표 페이지/화면·같은 실제 콘텐츠 |
| 시각 원리 | 제목/본문 비율·그리드·정렬·색의 역할·표면 구분·아이콘/이미지 정책 |
| 적용 계약 | 어떤 공통 컴포넌트·반복 페이지·상태에 어떤 토큰을 적용할지 |
| 판단 | 과업 적합성·가독성·브랜드 적합성·초기/포화·좁은 폭 또는 페이지 밀도 |
| 반복 위험 | 최근 이 프로젝트에서 이미 선택한 외형과 구조가 얼마나 유사한지 |

관찰한 값, 추정한 원리, 새 결과물의 채택 토큰을 분리한다. 문서에는 목차·본문·표/그림 대표면을, 앱·웹에는 주요 화면과 초깃값/포화 데이터를 포함한다. 시각 방향을 특정 레퍼런스와 1:1로 복제하지 않는다.

## 반복 외형과 기계 검사의 경계

같은 프로젝트의 최근 시안이 동일한 hero 구조·카드 반복·폰트 대비·색 배분을 반복하면 실제 화면을 병렬로 놓고 이유를 검토한다. 사용자가 이미 선호하거나 브랜드가 요구한 패턴은 기계적으로 금지하지 않는다. 다른 프로젝트의 취향 기록은 접근 가능한 승인된 자료가 있을 때만 사용하고, 사용자의 발언을 새 영구 저장소에 자동 기록하지 않는다.

실제 렌더에서 작은 글자, 낮은 대비, 깨진 자산, 의도치 않은 overflow, 반복된 장식 패턴을 도구로 탐지할 수 있다. 자동 검사는 문제 후보를 제시하고 사람이 근거를 검토한다. 스크립트의 exit 0, 스크린샷 저장, 경고 없음만으로 정렬·접근성·동작·편집 가능성이 증명되지 않는다. 구조가 다른 방향을 이미지 색상 거리만으로 동일/상이하다고 판정하지 않는다.

카드는 독립 정보 단위 또는 독립 행동·상태를 묶는 데 필요한 경우에 쓴다. 제목과 간격, 행·구분선, 컬럼, 배경 구획만으로 계층이 충분한지 비교한다. 포화 조건에서 카드 테두리·그림자·내부 padding이 콘텐츠를 얼마나 밀어내는지도 본다.

시각 방향 확인 C에는 같은 화면·콘텐츠의 대표 렌더 9개와 전체 크기 보기, 짧은 비교 근거, 추천안과 손해를 함께 제시한다. 선택 또는 축별 조합이 끝나면 새 방향 ID의 대표 화면을 다시 렌더해 확인받고 그 방향의 토큰·컴포넌트 스타일·사용 범위를 확정한다. 이후 실제 주요 화면·페이지를 제작하고 별도 검증 에이전트가 최종 렌더를 확인한다. [테마 탐색 기록 검사기](../scripts/check_theme_exploration.py)는 후보 다양성과 선택안 이월 근거의 누락을 경고한다.

제시 직전에는 방향별 명세표의 실측값, 선택 상태 서명의 일관성, 조작 무게, 뜻하지 않은 색·선·그림자, 축별 혼합 가능성을 실제 화면에서 확인한다. [브라우저 방향 측정기](../scripts/check_visual_direction_render.py)에 대표 요소 선택자를 넣어 상태 서명, 보조 조작 크기, 예기치 않은 검은 버튼, 앱바 경계, 방향 간 버튼·행·표면 서명의 같음을 경고받는다. [사용자 관점 리허설](design-contract.md#역할구성-대안-및-와이어프레임-비교)의 질문도 C 화면에 다시 적용한다. 검사기가 기록 누락과 문제 후보를 발견할 수는 있지만 구성·일관성·사용성의 PASS는 실제 비교 렌더를 보고 판정한다.
