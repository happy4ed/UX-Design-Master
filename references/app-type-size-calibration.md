# 앱 글자 크기 실측과 확정

앱의 기본 최소 글자 후보는 **14**다. 브라우저 모형에서는 CSS px로 비교하고, 실제 Android 앱에서는 sp, iOS 앱에서는 pt와 시스템 글자 설정으로 별도 구현·검증한다. CSS px·sp·pt를 같은 물리적 크기로 간주하지 않는다. 웹의 기본 하한 13 CSS px 및 인쇄 문서의 6.5pt 기준은 별개다.

## 발동 조건과 입력

새 앱의 타이포그래피를 정하거나 앱의 최소 글자 크기 변경을 제안할 때 확인 C에서 [실측 비교 화면](../samples/app-type-size-lab.html)을 실제 대상 기기로 연다. 최종 제품에서 쓸 글꼴과 현실적인 한글·영문·숫자 문구, 표시 조건, 주요 기기, 평소 보는 거리를 입력한다. 기기마다 브라우저/OS 확대 설정이 달라지면 다시 측정한다. 13px 행은 비교 자료일 뿐, 앱 기본 하한 후보가 아니다.

## 물리 크기와 선택

실물 자로 화면의 50mm 기준선을 맞춘 뒤 `mm / CSS px = 50 / 기준선의 CSS px`를 계산한다. 해당 글꼴의 실제 글리프 잉크 높이는 Canvas `TextMetrics.actualBoundingBoxAscent + actualBoundingBoxDescent`를 써서 근사하고, 보정 계수로 mm로 바꾼다. 보는 거리를 입력하면 시각 크기 `2 atan(잉크 높이 / (2 × 보기 거리))`를 표시한다. 자 보정을 하지 않았으면 물리 수치는 **미보정**으로 남긴다. DPR만으로 실제 화면의 mm를 확정하지 않는다.

같은 문장·글꼴·굵기·거리에서 13~18 CSS px를 나란히 읽고 `편함 / 경계 / 어려움`을 기록한다. 앱 최소값 제안은 편하게 읽힌 최소 크기와 현재 14 기준 중 큰 값에서 시작한다. 14보다 작은 값은 자동 채택하지 않고 예외의 위치·목적·확대 경로를 따로 제시해 사용자에게 확인받는다. 숫자·강조·상태 색이 바뀌는 실제 화면도 확인한다. 계산한 mm나 시각 크기만으로 가독성을 판정하지 않는다.

## 확대와 최종 검증

선택한 최소값으로 대표 앱 화면의 기본·150%·200% 글자 확대를 비교한다. 한 줄→여러 줄, 행 높이, 스크롤, 버튼과 금액의 위치, 잘림·겹침, 첫 화면의 핵심 행동 노출을 기록한다. 선택 결과에는 기기·뷰포트·글꼴·거리·보정 상태·편하게 읽힌 최소 후보·최종 선택·확대별 렌더 근거를 남긴다. 웹 모형은 물리 크기와 레이아웃을 미리 비교하는 도구이며 네이티브 글꼴 래스터와 Android의 sp, iOS의 Dynamic Type 배율을 완전히 재현하지 않는다. 앱 최종 결과물은 대상 기기의 시스템 글자 확대를 켜고 다시 캡처·조작해 검수한다.

## 실패 사례

- 데스크톱에서 임의로 축소한 휴대폰 프레임만 보고 크기를 확정한 경우: 실제 물리 크기 근거 없음.
- 화면의 글자 크기만 키우고 고정 높이 버튼·목록을 유지한 경우: 확대 상태의 잘림이나 가림이 발생한다.
- CSS px 숫자를 Android sp나 iOS pt의 실측값으로 보고한 경우: 플랫폼 단위와 글꼴 렌더 차이를 누락했다.
- 14px이 편하게 읽힌다는 이유만으로 모든 사용자와 기기에서 충분하다고 단정한 경우: 대상 기기와 글자 확대 검수가 빠졌다.
