# 화면 분석에서 실제 제작까지: 디자인 시스템 적용 계약

이 문서는 화면·문서의 역할과 구조를 분석한 뒤, 합의된 와이어프레임을 **실제 제작 규칙**으로 바꾸는 방법이다. 검수 체크리스트만 만드는 문서가 아니다. 새 디자인, 기존 결과물 개선, 재사용 시스템 구축에 공통으로 적용하되, 작업 범위에 맞는 규모로 작성한다. 분석 자료의 관찰값과 새 결과물에 채택한 값, 사용자 승인 상태를 섞지 않는다.

## 1. 분석 결과를 제작 입력으로 변환

화면·페이지별로 `영역/역할 → 콘텐츠/상태 → 컴포넌트 인스턴스 → 시각·기하 근거 → 채택 결정 → 구현 위치`를 연결한다. 같은 이름의 요소라도 기능·상태·데이터 경계가 다르면 별도 변형으로 기록한다. 출처 화면의 CSS 빈도는 역할을 증명하지 않으며, 스크린샷에서 보이지 않는 행동과 Z 깊이는 추정으로 표시한다.

| 필드 | 반드시 결정할 내용 |
| --- | --- |
| 영역과 계층 | 화면 전체 바탕, 영역·컴포넌트 표면, 오버레이의 소속·겹침·가림 |
| 역할과 사용 맥락 | 사용자 과업, 행동 결과, 단독/반복/공통 사용 여부 |
| 데이터 경계 | 최초·포화·긴 번역·오류·로딩·권한 조건과 텍스트 슬롯 |
| 실측과 선택 | 원본 관찰값, 새 제품의 제안값, 승인값의 별도 기록 |
| 위치 | 화면/페이지 ID, 컴포넌트 ID, 토큰 ID, 구현 파일 또는 디자인 노드 |

큰 개편이나 시스템 이전에서는 페이지 수만 세지 않고 **컴포넌트 인스턴스와 변형의 사용 빈도**를 집계한다. 공통 사용 폭, 과업 중요도, 접근성 위험, 구현 비용, 변경 전파 범위를 함께 보고 우선순위를 정한다. 스킬의 122개 기본 UI 정의는 후보 카탈로그이며 모두 제작할 목록이 아니다.

## 2. 기초 규칙을 먼저 명세하고 화면에 적용

확인 B 이후 구조 토큰을 정리하고, 확인 C에서 색·서체·자산을 선정한 뒤 확정값을 시스템에 반영한다. 최소 기초 규칙은 색 역할과 Z 층, 타이포그래피 계층, 간격·R·그리드, 크기·터치 영역, 그림자·블러, 모션 원칙이다. 문서 디자인에서는 페이지 격자·문단·표·그림 역할로 바꿔 적용한다. 모든 숫자를 한 배수에 억지로 맞추지 말고 예외를 이유와 소유 위치로 관리한다.

토큰은 가능한 경우 다음 의존 방향으로 사용한다.

`기초 값(primitive) → 의미 역할(semantic) → 컴포넌트 슬롯(component) → 화면/페이지 인스턴스`

- 기초 값은 색상 좌표·간격 값·서체 크기·시간처럼 재료를 담는다. 브랜드의 색상군 수와 각 색상군의 명도 단계 수는 서로 다른 결정이다.
- 의미 토큰은 `canvas.background`, `surface.background`, `text.primary`, `action.primary`, `status.error`처럼 **역할**로 이름 짓는다. `blue.500` 같은 재료 이름을 화면 역할로 쓰지 않는다.
- 컴포넌트 슬롯은 `button.primary.background`, `list.item.padding`, `dialog.title.type`처럼 특정 요소의 적용 위치를 나타낸다. 전역 기초 값을 개별 컴포넌트에서 바로 하드코딩하면 의미 변경이 전파되지 않으므로 이유가 있는 예외만 허용한다.
- 테마·상태·밀도·플랫폼별 값은 같은 역할의 대체 매핑으로 기록한다. 다크 테마를 단순 색 반전으로 생성하지 않는다. 각 화면/표면의 전경·배경 **짝**과 텍스트·상태 대비를 별도로 확인한다.
- 토큰 이름을 바꾸거나 삭제할 때는 사용 화면·컴포넌트와 이전 이름의 대체 경로를 확인한다. 재사용 시스템에는 변경 기록과 영향 범위를 남긴다.

색상 선택은 지각 명도·채도·색상각·대비를 각각 목적에 맞게 조정한다. 반투명 표면의 실제 배경, 그라데이션 구간, 상태 오버레이를 합성한 뒤 읽기성과 계층을 판단한다. 추출된 색상 빈도만으로 의미 토큰을 자동 지정하지 않는다.

## 3. 컴포넌트와 패턴을 제작 단위로 만들기

화면 사용 맵에서 실제 반복되는 요소부터 컴포넌트로 만든다. 컴포넌트는 역할·구성 슬롯·크기/밀도 변형·상태·입력 방식·데이터 제한·접근성·토큰 사용·사용 금지 조건을 가진다. 공통 요소인지 기능 집단 전용인지 화면 전용인지 표시한다. 비슷한 모양이라는 이유만으로 행동이 다른 요소를 합치지 않는다. 기존 컴포넌트 계약과 입력 계약을 따른다.

**패턴은 여러 컴포넌트를 묶은 과업 흐름**이다. 폼, 검색 결과, 파괴적 확인, 다단계 입력, 빈 상태와 복구, 문서의 비교 페이지처럼 개별 컴포넌트만으로 완결되지 않는 경우 작성한다. 최소 기록은 다음과 같다.

1. 사용자의 목표와 시작·완료·취소·복구 순서.
2. 필요한 컴포넌트, 각 컴포넌트의 소유 역할, 연결과 상태 전달.
3. 실제 문구와 정보 순서, 초기·포화·오류·느린 응답·긴 번역의 처리.
4. 키보드·터치·스크린리더 경로, 포커스 복귀, 모션 감소 대안.
5. 잘못된 사용 예: 같은 역할의 중복 버튼, 근거 없는 카드 포장, 파괴적 행동을 평범한 토스트로 끝내는 식의 구체적인 실패 조건.

패턴 명세는 선택한 와이어프레임과 확인 C의 시각 방향을 화면·페이지에 어떻게 조합할지 설명해야 한다. 새 패턴 이름을 만든 것만으로 제작 완료로 표시하지 않는다.

## 4. 대표 화면에서 시스템을 실제로 시험한 뒤 확장

확인 A1~D의 결정은 **최종물 이월표**로 연결한다. 각 결정의 ID, 최종 반영 위치, `사용자 기능/검토용 조작/적용하지 않음` 구분, 검증 화면을 한 행으로 적는다. 확인 C의 테마·화면 모드·밀도처럼 검토 도구에서 사용한 제어가 최종 사용자 기능으로 남는지 여기서 확정한다. 다크 모드를 최종 제품 범위로 채택했다면 사용자가 화면에서 고르고, 이동 뒤에도 선택이 유지되는지 확인한다. 범위 밖인 검토용 제어는 제품 설정처럼 보이지 않게 표시한다.

전체 화면에 일괄 적용하기 전에 공통 요소가 많이 교차하는 대표 화면/페이지를 만든다. 동일한 토큰·컴포넌트·패턴으로 초기와 포화 콘텐츠, 좁은 폭, 긴 한국어·영어·RTL, 밝고 어두운 테마(필요한 경우)를 적용한다. 레이아웃이 실패하면 그 화면의 좌표를 임시로 고치기 전에 어떤 공유 토큰·슬롯·데이터 계약이 원인인지 찾는다. 수정 범위를 사용 맵으로 추적한 뒤 다른 사용 화면에도 반영한다.

대표 화면이 안정되면 같은 규칙으로 나머지를 제작한다. 화면별 독립 CSS 값과 즉흥적인 예외가 늘어나면 공통 계약에 누락된 역할인지, 정당한 전용 변형인지 판정한다. 사용자에게 승인받은 색·폰트 방향을 바꾸는 결정은 다시 보여주고 선택받는다. 확인 D에서 모션 대상·강도를 정한 뒤 패턴 흐름에 실제 동작을 연결한다.

## 5. 기존 제품 이전일 때만 추가하는 경로

기존 값과 새 의미 토큰의 대응표를 만들고 전환 중에는 양쪽 사용 위치를 추적한다. 기계적인 교체는 자동화할 수 있지만, 같은 색이 서로 다른 의미로 쓰인 경우는 화면 역할을 다시 판단한다. 오래된 값은 처음에는 탐지·보고하고, 해당 영역의 이전이 끝난 뒤 금지 규칙으로 올린다. 이전 완료 기준은 토큰 치환율만이 아니라 핵심 흐름·상태·테마의 화면 일치와 기존 별칭을 제거할 수 있는지까지 포함한다. 단발 페이지 제작에는 별도의 이전 체계를 만들 필요가 없다.

## 제작 산출물과 다음 단계 연결

하나의 진행 명세에 `화면/페이지 사용 맵`, `기초·의미·컴포넌트 토큰 맵`, `컴포넌트 계약`, `패턴 구성`, `대표 화면 적용 결과`, `예외·변경 영향`을 유지한다. 작은 작업은 필요한 열만 쓴다. 이 명세는 **제작자가 화면을 만드는 입력**이며, 이후 [실제 화면·문서 검수](quality-review.md)는 명세와 렌더가 일치하는지 확인한다. 명세 작성 자체나 자동 검사 통과를 시각적 완성으로 간주하지 않는다.

### 제작 중 연결 검사기

재사용 요소가 있는 작업에서는 [예제 제작 명세](../assets/design-system-production-example.json)를 프로젝트에 맞게 작성하고 다음을 실행한다. 스크립트는 스킬 폴더에서 실행하거나 전체 경로로 지정한다.

```bash
python3 scripts/check_design_system.py --input production-system.json
python3 scripts/check_design_system.py --input production-system.json --baseline previous-system.json
```

`tokens`는 ID를 키로 하는 정의이며 `tier`(`primitive`/`semantic`/`component`)와 `type`이 필요하다. 기초 토큰은 `value`, 의미·컴포넌트 토큰은 `ref` 또는 theme별 `refs`를 쓴다. `components`는 각 컴포넌트의 `tokens`, `variants`, `states`를, `surfaces`는 화면 ID와 인스턴스 ID·컴포넌트·변형·상태를 기록한다. `contrastPairs`에는 실제 함께 쓰는 전경/배경 토큰 ID를 적는다. 이 내부 형식은 외부 디자인 토큰 교환 표준을 구현했다고 주장하지 않는다.

검사기는 없는 참조·순환·타입 불일치·theme 누락·사용 맵의 없는 컴포넌트를 **오류**로, 기초값 직결·미기록 슬롯·전경/배경 짝 누락을 **경고**로 보고한다. 기본 실행은 오류만 종료 코드 1이며 `--strict`는 경고도 실패로 처리한다. `--baseline`은 추가·삭제·변경된 토큰과 영향받는 토큰·컴포넌트·화면을 보고한다. 영향 목록은 사용 맵에 기록된 관계만 추적하므로 누락된 인스턴스나 실제 CSS 사용을 찾아내지는 못한다. 색 대비 수치와 화면 품질도 렌더 단계에서 따로 검사한다.
