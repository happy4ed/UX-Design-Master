# 컴포넌트 모션 판단과 합의

앱·웹·문서에서 컴포넌트가 등장했다는 이유만으로 움직임을 넣지 않는다. 상태 변화·위치 변화·관계 이해에 필요한 경우를 먼저 찾아 **모션 후보**와 **정적 피드백**을 함께 설계한다. 최종 효과를 적용하기 전에는 사용자에게 짧은 실제 시연을 보여주고 선택을 확인한다. 사용자가 앞서 모션 방향을 명시했으면 그 선택을 재사용한다.

개별 효과의 적합성만 판단하지 말고 [자연스러운 모션의 화면·흐름 계약](natural-motion.md)으로 즉시 피드백, 공간 연속성, 설명, 장식의 역할과 한 화면의 움직임 밀도를 함께 검토한다. 입력 직후 상태 피드백과 실제 처리 완료의 시점을 구분한다.

## 1. 화면 전체의 변화 목록 만들기

각 화면의 **모든 실제 컴포넌트 인스턴스**에 대해 `트리거 → 바뀌는 상태/정보 → 사용자에게 필요한 피드백 → 정지 화면에서의 표시`를 쓴다. 버튼·리스트·스크롤 세 가지 예시로 검토 범위를 끝내지 않는다. [122개 기본 컴포넌트의 사건·판단 목록](../knowledge/component-motion-coverage.json)은 누락 점검용이다. 이름 붙은 시나리오는 [앱 상호작용 목록](../knowledge/app-motion-scenarios.json)과 [컴포넌트 상태 사건 목록](../knowledge/component-motion-scenarios.json)에서 찾는다. [기본 무모션 판단](../knowledge/component-no-motion-defaults.json)은 구조·표현 요소가 자체 사건 없이 놓인 경우에만 적용한다. 인스턴스에 실제 상태 변화가 생기면 판단을 다시 한다. 이 목록들은 전부 움직이라는 지시가 아니며, 실제 구현이나 검증 완료를 뜻하지 않는다. 데이터 자체가 변하지 않는 호버 장식은 후보에서 낮춘다. 상태가 사라지거나 항목 순서가 바뀌면 사용자가 전후 관계를 잃는지 확인한다. 화면에 같은 역할의 요소가 여럿 있으면 공통 모션 계약을 한 번 정의하고 예외만 적는다.

사건과 상태를 정한 뒤 [모션 × 컴포넌트 지식 그래프](motion-component-graph.md)에서 해당 컴포넌트·활용 유형·움직임 규모의 후보를 찾는다. 그래프의 연결은 적용 후보이므로 실제 화면의 중간·종료 상태를 시연한 뒤 채택한다.

앱·웹의 탭 선택, 스위치 실패 복귀, 목록 스와이프, 시트 끌기처럼 **과업 사건의 이름으로 소통해야 하는 경우** 두 시나리오 목록의 한국어/영어 이름과 컴포넌트·사건·전후 상태를 조회한다. `python3 scripts/query_app_motion.py --component bottom-sheet`, `--component divider` 또는 `--query "완료 링"`으로 찾는다. 조회 결과의 `candidate-only` 상태와 기본 무모션 근거를 함께 읽는다. 시나리오는 고유 모션 수에 더하지 않으며 구현 완료 목록도 아니다. 같은 시나리오에 여러 움직임을 적용할 수 있고, 같은 움직임을 여러 시나리오에 재사용할 수 있다. 후보를 제품에 넣으려면 실제 동작을 시작·중간·끝과 취소·역전에서 검증하고 사용자 확인 D에 올린다.

변화 목록의 각 후보에는 **사용 빈도와 목적 판정**을 먼저 붙인다. 하루 수십·수백 번 쓰는 키보드·반복 조작은 즉각적인 정적 피드백을 우선하고, 드문 완료·온보딩·설명 장면은 의미가 있으면 더 긴 전환을 검토한다. 목적은 피드백·공간 관계·상태 표시·갑작스러운 변화를 잇기·설명 중 하나로 적고, 어느 목적에도 맞지 않는 효과는 제외한다. 선정 후보뿐 아니라 탈락 후보와 이유를 남긴다. 300ms 같은 단일 시간 상한을 데이터 설명·발표·전시·영상에 일괄 적용하지 않고 사용 맥락과 실제 사용자의 반응으로 시간을 정한다.

손가락·마우스 드래그가 직접 구동하는 모션은 시간표로 시작하지 않는다. 대상이 포인터를 따라가는 비율, 경계에서의 저항, 놓을 때의 위치와 속도, 도착점 선택, 진행 중 다시 잡는 위치를 계약으로 기록한다. 놓는 순간의 실제 속도를 관성·스프링에 전달하고, 재포착은 목표 좌표가 아니라 **현재 렌더 위치**에서 이어간다. 버튼 눌림이나 시스템이 시작한 상태 전환은 별도의 시간 기반 계약으로 다룬다. 앱·웹 구현은 각 플랫폼에서 실제 제공하는 제스처/모션 기능을 확인해 선택한다.

| 컴포넌트·사건 | 모션 판단 | 기본 정적 피드백 | 권장 후보와 금지할 혼동 |
| --- | --- | --- | --- |
| 버튼 눌림·제출 | 응답 지연/중복 제출 위험이면 짧은 눌림 피드백과 진행 상태가 유용 | 눌림·로딩·완료·오류의 텍스트/아이콘/disabled 상태 | 눌림은 작은 scale/색 변화, 로딩은 진행 의미가 있을 때만. 결과를 기다리게 하는 장식 재생 금지 |
| 버튼 hover/focus | 입력 수단이 다르므로 hover만으로 의미를 전달하지 않음 | focus ring과 명확한 라벨 | hover 강조는 약하게, focus 표시를 모션에 의존하지 않음 |
| 리스트 추가·삭제 | 항목 위치가 변해 추적이 어려우면 짧은 진입/퇴장 | 추가·삭제 결과와 되돌리기 경로 | opacity/translate. 삭제 전 항목의 조작 가능 상태를 오래 유지하지 않음 |
| 리스트 재정렬·필터 | 앞뒤 위치 관계가 중요하면 FLIP 또는 레이아웃 전환 | 변경된 정렬 기준·항목 수·선택 유지 | 이동을 짧게 보여주되 대량 변경은 즉시 갱신 또는 집단 전환. 인덱스를 항목 ID로 오인하지 않음 |
| 스크롤·고정 헤더 | 현재 위치/구간 인지가 어렵다면 진행 표시나 헤더 축소 | 현재 섹션, 스크롤바, 앵커 | 스크롤과 1:1로 연결한 진행 표시. 기본 스크롤에 바운스/패럴랙스 자동 추가 금지 |
| 탭·아코디언·모달 | 내용/공간 관계가 바뀌면 짧은 전환 | 선택 상태, 열린 제목, 포커스 이동 | 높이 변화는 내용 재흐름과 동기화. 숨긴 내용의 포커스·스크롤 접근 확인 |
| 토글·체크·선택 | 상태의 즉시 인지가 필요 | checked/selected 상태와 라벨 | 핸들 이동은 상태와 동기화. 색과 이동만으로 상태 전달 금지 |
| 차트·다이어그램 | 시간·순서·양의 변화가 데이터 의미일 때 | 최종 값·범례·정적 관계 | 데이터 변화량에 연결한 전환. 숫자 의미 없는 무한 펄스 금지 |

## 2. 후보별 필수 명세

`컴포넌트/역할, 사건, 이전/다음 상태, 모션 목적, 정적 피드백, 대상 속성, 시작/끝, 시간 범위, 이징, 재입력·역전·취소, 화면 밖 처리, 키보드/터치, 모션 감소, 성능·레이아웃 영향, 사용자 결정`을 기록한다. CSS 속성의 숫자는 프로젝트의 모션 토큰으로 묶고 대표 화면에서 조정한다. 모든 전환을 같은 속도로 맞추거나 `transition: all`을 쓰지 않는다.

[모션 시간과 검토 속도](motion-timing.md)의 역할별 시작 범위에서 시간을 정한다. 이 숫자는 제품에 자동 적용할 표준값이 아니다. 화면 크기·이동 거리·입력 방식·콘텐츠 밀도·브랜드 방향과 사용자의 선택에 따라 조정한다. 큰 이동과 반복은 별도 근거가 있어야 한다. **시연 1×는 제품의 실측 속도가 아니다.** 모션 실험실에서는 관찰용 기준 시간과 조절 배율을 함께 표시한다.

**강도와 느낌은 별도의 축이다.** 강도는 이동 거리·크기 변화·지속 시간을 바꾼다. 느낌은 속도 곡선과 끝점의 성격을 바꾼다. 텐션은 목표점을 약간 지나 돌아오는 곡선, 릴랙스는 길게 감속하는 곡선, 중립은 완만한 종료다. [내부 프리셋](../assets/layout/component-motion-presets.mjs)과 [TypeScript 선언](../assets/layout/component-motion-presets.d.mts)은 `정지/미세/절제/표준/강조/극적` 여섯 강도와 `중립/정밀/경쾌/텐션/릴랙스/스프링/엘라스틱/일정/계단` 아홉 느낌을 독립적으로 비교한다. 이 수치는 검토용 시작값이다. 같은 거리에서 중간 위치와 오버슈트가 실제로 구별되는지 렌더에서 본다. 콘텐츠 이동·모달·입력 오류에 같은 오버슈트를 기계적으로 적용하지 않는다.

확인 D에서 정적/절제/표현적을 비교한다면 **세기의 숫자뿐 아니라 효과 종류의 차이**를 적는다. 절제는 필요한 상태·공간 전환을 중심으로, 표현적은 과업에 맞을 때 첫 진입의 순차 등장, 화면에 처음 들어온 차트의 성장, 숫자 변화, 시트의 정착감 같은 사건을 추가 후보로 검토한다. 표현적이 모든 후보를 자동 채택한다는 뜻은 아니다. 자동 등장은 첫 진입과 재진입의 차이를 정하고, 차트는 사용자가 보는 시점에 재생되도록 관찰 트리거를 정의한다. 같은 장식의 무한 반복이나 정보를 가리는 연출은 강도와 관계없이 제외한다.

## 2a. 효과 후보 사전

기존 48종은 CSS 단일 효과의 내부 시작점이다. 더 넓은 카메라·타이포·데이터·아이콘·도식 어휘와 UI 적용 조건은 [넓은 모션 어휘](motion-vocabulary.md)를 읽는다. 용어 목록 414개와 One UI 9 스타일의 실제 재생 레시피 43개는 구현 상태가 다르다. 화면의 사건에 맞는 레시피를 선택하고, 없는 동작은 이름만 채택하지 말고 구현·축소 대안·렌더 시험을 추가한다.

[CSS 효과 48종](../assets/layout/component-motion-effects.mjs)과 [실제 키프레임](../assets/layout/component-motion-effects.css)은 등장·피드백·공간·흐름·주의·로딩 여섯 묶음으로 정리한다. 효과 이름을 먼저 고르지 말고, 화면의 사건과 목적에서 후보를 좁힌다. 48개 각각의 용도는 카탈로그에 기록되어 있다. 주요 예시는 다음과 같다.

| 의미 | 후보 | 검토할 점 |
| --- | --- | --- |
| 새 정보의 진입·퇴장 | fade, rise, drop, slide, zoom, wipe, iris, blur | 기존 위치와 다음 위치를 오해하지 않는가 |
| 터치·선택·착지 피드백 | pop, bounce, spring, glow, color-shift, squash, ripple | 반응이 입력보다 늦거나 결과를 가리지 않는가 |
| 공간·앞뒤 관계 | flip-x, flip-y, tilt, float, orbit, swing, drift, hinge | 회전 중 텍스트가 읽히는가, 단순 정보에 장식이 과한가 |
| 상태 주목 | pulse, breathe, heartbeat, shake, wobble, nudge | 무한 반복이 집중을 방해하지 않는가, 정적 상태가 명확한가 |
| 진행·대기 | spin, loading-bob, skeleton, progress, loop-swap | 실제 작업 상태·진행값과 연결되는가 |

[반복 재생 검토 화면](../samples/component-motion-review.html)에서 48개를 한 번에 보고 강도·이징·재생·정지를 바꿀 수 있다. 아홉 이징은 같은 거리와 시간의 동시 비교로 확인한다. 검토 화면은 기기의 모션 감소 설정과 별개로 자동 재생을 기본 활성화하며, 체크박스를 끄면 해당 기기 설정을 따른다. **반복은 후보를 비교하기 위한 시연 방식**이다. 제품에서는 대부분 사건이 발생할 때 한 번 재생하고 상태를 유지한다. 좁은 화면과 모션 감소 설정에서 정보가 사라지지 않아야 한다.

판정 결과는 세 가지다.

- **필요 후보:** 전후 위치·상태·진행을 정적 표시만으로 따라가기 어렵다. 모션을 제안하되 정적 피드백도 유지한다.
- **선택 후보:** 이해에는 필수가 아니지만 조작 감각이나 브랜드 표현에 도움이 될 수 있다. 정적/절제/표현적 안을 비교한다.
- **불필요:** 상태가 바뀌지 않거나 효과가 집중을 방해한다. 정적 처리를 권한다.

## 3. 사용자와 반드시 확인할 때

시각 방향 확인 C 이후, 최종 모션 구현 전에 **모션 확인 D**를 둔다. 화면별 전체 변화 목록과 필요/선택/불필요 판단, 정적 상태, 주요 상호작용 유형별 실제 재생 시안을 제시한다. 인터랙션·흐름이 있는 매체는 [동작하는 프로토타입 계약](interactive-prototype.md)에 따라 핵심 경로를 실제 조작 가능한 화면으로 연결해 함께 보여준다. 여섯 강도와 아홉 느낌 중 화면의 사건에 적합한 후보를 좁혀 실제 재생으로 비교하고 추천 이유를 적는다. 어떤 컴포넌트에 어떤 조합을 적용할지 묻는다. 모든 요소에 같은 효과를 일괄 적용할지 묻지 않는다. 사용자가 고른 대상·강도·느낌·제외 대상을 기록해 승인된 범위에만 적용한다. 명시적 기존 선호가 있으면 다시 묻지 않고 해당 선호를 시안에 반영한다. 모션을 거부해도 필요한 상태 피드백은 정적 형태로 남긴다.

[컴포넌트 모션 검토 화면](../samples/component-motion-review.html)은 버튼·선택·탭·목록·메뉴·대화상자·진행률·캐러셀 등과 122개 기본 요소의 사건 후보를 살펴보는 내부 시안이다. 이 페이지에서 강도나 이징을 바꾸는 행위만으로 실제 프로젝트의 모션 방향이 승인된 것으로 해석하지 않는다.

질문 예: “목록 정렬 시 항목의 이전 위치를 따라가기 어렵습니다. 정렬 상태 표시는 유지하면서 180ms 위치 이동을 제안합니다. 정적 전환, 절제된 위치 이동, 더 강조된 위치 이동 중 어느 쪽이 맞을까요? 버튼 눌림은 별도로 100ms 피드백을 제안합니다.”

## 4. 매체별 적용

- **웹/CSS:** `:hover`, `:focus-visible`, `:active`와 상태 클래스에 역할별 토큰을 쓴다. 작은 색·transform/opacity 변화는 CSS transition, 시작/종료 상태가 복잡하거나 중단 제어가 필요하면 Web Animations API를 사용한다. `prefers-reduced-motion`에서 공간 이동·반복을 제거한다. [CSS 예제](../assets/layout/component-motion.css)를 복사하기 전에 제품 토큰에 맞춘다.
- **React/TypeScript:** 상태를 컴포넌트의 단일 진실 원천으로 두고 클래스/ARIA/disabled와 모션을 함께 바꾼다. 리스트는 안정적인 item ID와 이전/다음 위치 측정으로 이동을 제어한다. 재렌더·언마운트 때 애니메이션을 취소하고 reduced motion을 따른다. 단순 버튼 전환에 전역 모션 라이브러리를 강제하지 않는다.
- **네이티브 앱:** 같은 상태표와 시간·거리·중단 정책을 플랫폼의 기본 애니메이션 기능으로 옮긴다. 웹 CSS 속성을 그대로 이식하지 않는다. 시스템의 모션 감소 설정, 뒤로 가기 제스처, 화면 전환과 스크롤 관성을 함께 확인한다. 플랫폼별 구현 API는 실제 프로젝트 버전을 확인해 고른다.
- **문서:** 정적 PDF·인쇄물의 의미와 읽기 순서를 우선한다. 브라우저 문서·프레젠테이션에서만 단계 공개가 이해를 돕는 경우에 한해 별도 정적 버전과 함께 제안한다.

React/TypeScript의 상태 연결 예:

```tsx
type SaveState = 'idle' | 'loading' | 'done' | 'error';
function SaveButton({save}: {save: () => Promise<void>}) {
  const [state, setState] = React.useState<SaveState>('idle');
  async function submit() {
    if (state === 'loading') return;
    setState('loading');
    try { await save(); setState('done'); }
    catch { setState('error'); }
  }
  return <button className="motion-button" type="button" data-state={state}
    aria-busy={state === 'loading'} disabled={state === 'loading'} onClick={submit}>
    {state === 'loading' ? '저장 중…' : state === 'done' ? '저장 완료' : state === 'error' ? '다시 시도' : '저장하기'}
  </button>;
}
```

모션은 `data-state`에 대한 CSS 또는 상태 전환 시 실행되는 Web Animations API가 맡는다. 네이티브 앱도 같은 `idle/loading/done/error` 상태를 먼저 구현하고 해당 플랫폼의 전환 기능을 연결한다.

## 5. 렌더 검수

각 승인된 효과를 실제 대표 화면에서 처음·중간·끝 프레임과 빠른 재입력·역전·취소로 확인한다. 버튼은 입력이 즉시 반응하는지, 리스트는 항목의 ID와 포커스가 유지되는지, 스크롤은 위치와 내용이 어긋나지 않는지 본다. 60Hz 이상 기기에서 프레임 지연을 확인하고 레이아웃을 매 프레임 다시 계산하는 효과를 줄인다. 화면 밖에서만 움직이거나 `prefers-reduced-motion`에서 정보가 사라지면 실패다.

제스처 모션은 **드래그 시작 → 진행 중 방향 전환 → 놓기 → 감속 중 다시 잡기 → 취소/완료**를 한 번에 시연한다. 손가락과 대상 사이의 거리, 손을 놓는 속도와 이후 움직임의 연속성, 경계에서 튀거나 끊기는 프레임을 기록한다. 원본 효과의 중복 판정용 정지 프레임과 실제 제품 제스처의 품질 검사는 다른 PASS로 관리한다.

반복 입력이 가능한 전환은 중간 상태에서 다시 누르거나 반대로 조작했을 때 시작점으로 튀지 않는지 확인한다. 실제 웹 구현은 사용 대상에 가까운 중간급 기기와 지원 주사율에서 프레임 기록을 남기고, 코드에서 예상한 성능과 실제 프레임 결과를 구분한다. 실측이 없으면 성능 PASS로 표시하지 않는다.
