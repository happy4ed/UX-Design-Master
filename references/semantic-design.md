# 화면 의미 분석과 역할 기반 대안 설계

## 공통 순서

화면/과업 읽기 → 목적·정보·상태·행동·영향 관계 정의 → 필요한 역할과 요소 정의 → 역할을 수행하는 구성 대안 → 근거 확인 → 측정·도면·와이어프레임. 원본을 열거나 읽기 위한 도구는 사용하되, 자동 요소 추출·좌표 측정·코드 생성 결과가 의미 분석을 대신하게 하지 않는다.

시각 형태, 제품에서의 의미 역할, 구현 컴포넌트/접근성 역할을 서로 다른 필드로 기록한다. 둥근 사각형이라는 이유로 button, 캡슐 두 개라는 이유로 tabs, 색이 바뀐다는 이유로 toggle이라고 확정하지 않는다. 하나의 시각 그룹이 여러 의미 요소를 포함할 수 있다. 그룹 경계와 실제 상호작용 단위를 구별한다.

## 제공된 화면: 먼저 읽고 관계를 설명

1. 제목·레이블·설명·값·상태·이미지 내용을 읽고 화면의 목적과 사용자의 현재 과업을 한 문단으로 설명한다. 읽을 수 없는 내용은 미확인으로 남긴다.
2. 탐색, 콘텐츠, 입력·선택, 명령, 피드백, 보조 영역을 구분한다. 어떤 영역이 다른 영역을 제어하는지 연결한다.
3. 요소마다 아래 명세를 작성한다. 정보 표시용 요소와 장식도 구분하며 모든 요소를 조작 가능한 것으로 가정하지 않는다.
4. 상호작용을 관찰할 수 있으면 가설을 확인한다. 정적 이미지뿐이면 역할 후보·근거·미확인·확인 방법을 남긴다. 불확실한 요소를 임의 확정하지 않아도 나머지 분석은 진행할 수 있다.
5. 의미 분석 후 anatomy·재사용 범위·콘텐츠 계약을 정하고 측정·도면화한다. 보고서는 의미 명세를 치수 표보다 먼저 보여준다.

| 필드 | 내용 |
| --- | --- |
| 요소 ID·소속 | 어느 화면·영역·의미 그룹 안에 있는가 |
| 내용·사용자 의도 | 무엇을 읽거나 무엇을 하려는가 |
| 의미 역할 / 형태 | 예: 기간 필터 / 캡슐형 단일 선택 그룹 |
| 입력·전후 상태 | 무엇을 하면 어떤 값·선택·화면·상태가 바뀌는가 |
| 영향 대상 | 자신 / 지정 콘텐츠 영역 / 전체 화면 / 다른 화면 / 저장 데이터 |
| 선택·확정·유지 | 단일/다중, 재선택 해제, 즉시/확인 후 적용, 유지 범위·기간 |
| 근거·확신 | 관찰 / 동작 확인 / 추정 / 미확인 및 다음 확인 방법 |

정보 요소에는 적용되지 않는 행동 필드를 N/A로 기록한다. 버튼의 눌린 순간과 지속적인 선택 상태를 구별한다. disabled·loading은 의미 역할이 아니라 별도 상태 축이다.

## 화면 안의 조작 중복 검사

각 화면의 조작을 하나의 표로 모아 비교한다. 필터·정렬·보기 전환·탐색을 각각 정의한 뒤에도 같은 결과 집합이나 순서를 만들 수 있으므로 **확인 B 전에** 실제 자료와 상태를 넣어 함께 실행한다.

| 조작 ID | 대상 자료 | 바뀌는 것 | 결과 집합·순서 | 출처(사용자/제안) | 중복 판정·유지 이유 |
| --- | --- | --- | --- | --- | --- |

두 조작이 같은 결과를 내면 하나로 합친다. 둘 다 필요하면 서로 다른 사용자 과업과 상태 차이를 기록한다. 사용자가 요청하지 않은 정렬·필터 선택지는 기본 와이어프레임에 넣지 않고 제안으로 분리한다. 이름만 다르고 결과가 같은 조작, 실제 자료에서 결과가 바뀌지 않는 조작, 필터가 이미 만든 부분집합을 정렬 이름으로 다시 표현한 조작은 재검토한다.

[조작 중복 검사기](../scripts/check_control_overlap.py)에 실제 fixture별 결과 ID의 순서와 `purposeTags`를 넣으면 동일 결과·목적 겹침을 경고한다. 한 fixture에서 같아도 다른 경계에서는 달라질 수 있으므로 경고를 실제 과업으로 판정한다. 검사기 PASS를 조작 설계 품질의 PASS로 해석하지 않는다.

## 혼동하기 쉬운 역할 판별

다음은 분류할 때 확인할 질문이며, 정적 이미지에 행동을 덧붙이는 규칙이 아니다.

| 후보 | 먼저 확인할 의미 | 구별할 대상 |
| --- | --- | --- |
| tab | 연관된 콘텐츠 패널/뷰 중 현재 보여 줄 것을 선택하는가 | 같은 데이터의 필터, 설정값 선택, 다른 경로로 이동하는 링크 |
| switch | 이름 붙은 이진 설정/기능의 on/off 상태를 바꾸는가 | 명령 실행, 다중 선택 항목, 임시 눌림 상태 |
| command button | 실행·저장·열기 등 사건을 일으키는가 | 이동하는 링크, 지속 선택을 가진 toggle button |
| toggle button | 같은 명령/모드의 지속적인 pressed 상태를 반전하는가 | 순간 pressed 피드백, switch 형태의 이진 설정 |
| checkbox | 선택 집합의 항목 포함 여부 또는 동의 값을 바꾸는가 | 상호 배타적인 한 값 선택 |
| radio / 단일 선택 그룹 | 한 변수의 대안 중 하나를 선택하는가 | panel을 전환하는 tabs, 독립적인 복수 toggle |
| segmented control | 우선 시각적 표현 명칭. 실제 역할은 뷰 전환·필터·값 선택 중 무엇인가 | 형태만으로 tab/radio/toggle을 확정하는 것 |
| link / 탐색 행 | 위치·리소스·화면으로 이동하는가 | 선택값 변경, 직접 명령 실행 |
| slider | 범위 내 값을 조정하는가. min/max/step/즉시 반영 여부는 무엇인가 | 단순 진행률·게이지·스크롤바 |
| menu / popover / dialog | 표면 안 내용은 명령 목록인가, 보조 정보인가, 별도 과업인가. 모달성은 무엇인가 | 모든 떠 있는 표면을 같은 역할로 취급하는 것 |

구현 시에는 선택된 제품 의미에 맞는 플랫폼 컴포넌트·네이티브 의미와 입력 방식을 확인한다. 역할 이름을 붙였다는 이유로 ARIA 속성만 기계적으로 추가하지 않는다.

현재 표본의 예: Last 24 hours / Last 7 days는 기간 필터 후보다. 실제로 무엇이 바뀌는지 확인 전 tabs로 단정하지 않는다. Weekdays / Weekends는 설정 대상 문맥의 단일 선택 후보지만, 저장값 선택인지 편집 대상 전환인지 미확인이다. Learn more는 추가 정보를 여는 행동 후보이며 이동/패널 열기는 미확인이다.

## 신규 디자인: 역할에서 요소와 구성 variation으로

1. 사용자 목표 → 필요한 정보·판단 → 필요한 행동 → 역할 → 요소/구성 후보를 연결한다. 처음부터 익숙한 컴포넌트 이름으로 요구사항을 대체하지 않는다.
2. 역할별 필수/선택 요소와 데이터·상태·영향 대상을 정의한다. 빠진 역할, 중복 역할, 주 행동과 경쟁하는 보조 행동을 찾는다.
3. 같은 역할의 구현 후보와 화면 구성 대안을 만든다. 예: 짧은 단일 값 선택의 radio/segmented/select, 좁은 화면의 inline/disclosure/별도 화면. 각 후보의 의미·정보 발견성·조작 수·공간·데이터 증가·접근성 차이를 설명한다. 서로 다른 의미의 tab과 switch를 단순 외형 대체재로 비교하지 않는다.
4. 역할이 바뀌는 대안은 과업·상태 모델이 어떻게 바뀌는지도 명시한다. 시각 variant, 상태, 구조 대안을 섞지 않는다. 모든 요소의 전 조합을 생성하지 말고 사용자 과업과 핵심 불확실성을 바꾸는 대안을 비교한다.
5. 역할·요소 명세는 확인 A1, 과업의 전개는 A2, 화면별 역할·구성 대안은 A3에 연결하고, 승인된 요구사항으로 아래 와이어프레임 비교를 수행한다.

## GUI 이전 필수: 최소 3개 와이어프레임 대안

신규 디자인과 주요 개편에서는 동일 요구사항·핵심 과업·콘텐츠 범위에 대해 서로 구별되는 와이어프레임 대안을 **최소 3개** 제작한다. 다른 페이지 3장, 상태 3개, 색·폰트·R만 바꾼 3개는 구조 대안으로 세지 않는다. GUI 시안부터 만든 뒤 색을 빼서 와이어프레임 단계로 소급하지 않는다.

- 정보 구조·위계, 탐색, 주 행동 위치, 콘텐츠 그룹·배치, 점진적 공개 등 의미 있는 구성 차이를 둔다. 장단점이 없는 형식적인 열등안을 수 채우기로 만들지 않는다.
- 각 대안은 같은 대표 화면/과업 범위를 보여주고 복잡한 흐름은 관련 키 프레임을 함께 제시한다. 비교용 콘텐츠와 조건을 맞춘다.
- 각 대안의 주요 화면은 Initial/Saturated 두 경계에서 같은 규칙으로 구성한다. 필요한 좁은 폭·글자 확대 조건도 비교한다.
- 목적 적합성, 정보 발견성, 주 행동 명확성, 조작·전환 비용, 데이터 증가 대응, 좁은 폭·접근성, 공통 컴포넌트 재사용을 비교한다. 비슷한 이미지의 취향 투표로 끝내지 않는다.
- 가장 적합한 안을 추천하되 사용자 과업·제약에 연결해 이유와 손해를 설명한다. 나머지 안도 모두 실제 와이어프레임으로 보여 주고 장점·적합한 상황·이번에 추천하지 않은 이유를 설명한다. 사용자가 다른 안을 선택하거나 장점을 조합할 수 있게 한다.
- 확인 B에서 선택/수정한 구성과 남은 쟁점을 기록한다. 합성안은 바뀐 와이어프레임을 보여 주고 확인받는다. 사용자 확인 전에 GUI 스타일링·최종 시각 디자인으로 넘어가지 않는다.

| 대안 | 해결 전략·구조 차이 | 과업·행동 경로 | 초기/포화·좁은 폭 | 장점·손해 | 추천 판단·근거 |
| --- | --- | --- | --- | --- | --- |
| A | 실제 와이어프레임 연결 | 동일 과업 | 같은 조건 | 둘 다 기술 | 조건과 연결 |
| B | 실제 와이어프레임 연결 | 동일 과업 | 같은 조건 | 둘 다 기술 | 조건과 연결 |
| C 이상 | 실제 와이어프레임 연결 | 동일 과업 | 같은 조건 | 둘 다 기술 | 조건과 연결 |

임의 가중치·점수로 객관성을 꾸미지 않는다. 점수를 쓴다면 기준·가중치·추정 근거를 공개하고 합격할 수 없는 제약은 별도 표시한다. 작은 수정·참고 분석만의 작업에는 신규 3안 제작을 강제하지 않는다. 사용자가 명시적으로 위임·생략한 범위는 기존 승인 원칙에 따른다.
